# 같은 작업 트리에서 이종 에이전트 2개 동시 작업

종류: 리서치 · 작성: 2026-09-18 claude(다중 에이전트 워크플로 2차) · 웹 사실은 URL과 확인 날짜 기준. 판정은 `../05-concurrency-and-handoff.md`.

## 주제
같은 작업 트리에서 벤더가 다른 에이전트 2개(Codex=애니메이션·Blender MCP·언리얼 에디터 MCP, Claude=전투 C++·빌드·라이브 코딩·PIE 테스트)가 동시에 작업할 때의 상태 공유·충돌 방지 기술 조사 — (1) 공용 텍스트 파일 추가 전용 쓰기의 Windows 동시성과 벤더 편집 도구의 쓰기 방식, (2) 단일 자원(언리얼 에디터 MCP 1개·Blender MCP 1개) 조정과 UE 5.8 MCP 서버의 다중 세션 동작, (3) git 워크트리·브랜치·커밋 섞임, (4) 2026년 다중 에이전트 보드·잠금 도구의 2-에이전트 적합성. 조사일 2026-09-18, 저장소 C:\Project\TDGame(Windows 10, UE 5.8).

## 핵심 사실
- [1-a 추가 전용 쓰기] Windows에서 흔한 도구의 append는 원자적이지 않다. UCRT(Universal C Runtime) `_write`는 FAPPEND면 `_lseeki64_nolock_internal(fh,0,FILE_END)` 후 WriteFile(seek-then-write)이라 Python `open(...,'a')`가 프로세스 간 교차·덮어쓰기 가능(write.cpp 727~730행). .NET Core는 FileSystemRights.AppendData가 없어 PowerShell Add-Content/Out-File -Append도 같다(dotnet/runtime #53432). 예외는 Cygwin/MSYS2 계열(Git Bash `>>`)의 원자 O_APPEND뿐이다. FILE_APPEND_DATA로 직접 열어도(ctypes/pywin32) 한 항목이 단일 WriteFile 호출이어야 원자적이다.
- [1-b 잠금] 표준 라이브러리 `msvcrt.locking(LK_NBLCK, 1바이트)`가 filelock·portalocker(v4.0.0+, pywin32 불필요)의 Windows 구현이며, 프로세스가 죽으면 OS가 해제하므로 '죽은 세션'에도 안전하다. mkdir 잠금(`os.mkdir` → FileExistsError)은 NTFS에서 원자적이고 소유자 파일(agent·pid·시각)을 같이 두면 stale 회수를 pid 생존 검사로 결정론화할 수 있다. Worklog 같은 append-only 장부는 (가) 잠금 안에서 append하는 스크립트 1개로 쓰거나 (나) 에이전트별 파일(`Docs/Worklog/2026-09-<agent>.md`)로 쪼개 동시 쓰기 자체를 없애는 것이 가장 싸다.
- [1-c SQLite WAL] WAL(Write-Ahead Logging, 미리 쓰기 로그)은 로컬 NTFS의 두 프로세스에 잘 맞고(같은 호스트 필수, 읽기는 쓰기를 안 막음, 쓰기는 한 번에 하나, `sqlite3.connect(timeout=5.0)` 기본 대기), 장부 정본을 DB로 두고 마크다운을 생성하는 방식은 기술적으로 가능하다. 그러나 DB 파일은 git diff로 검토할 수 없고(사용자 조건 위반), 커밋하려면 JSONL(JSON Lines) 내보내기 단계가 추가되며, 에이전트 2개·세션당 항목 1~3개 규모에서는 잠금 1개짜리 append 스크립트와 결과가 같다. 2-에이전트 규모에서는 이득이 없다.
- [1-d 벤더 편집 도구] 세 벤더 모두 '메모리에서 부분 치환 → 디스크에는 파일 전체 재작성'이다. Claude Code Edit/Write는 마지막 Read 이후 mtime이 바뀌면 'File has been modified since read'로 차단하고(#28383), Write는 Read 없이 기존 파일을 덮어쓰지 못한다(이 세션의 도구 설명에서 확인) → Claude가 남의 변경을 덮어쓰는 일은 막히지만, Codex apply_patch(derive_new_contents_from_chunks → fs.write_file, mtime·해시·rename 검사 없음)와 Antigravity(write_to_file·replace_file_content·multi_replace_file_content, 검사 문서 없음)는 Claude가 방금 바꾼 파일을 읽은 시점의 내용으로 되돌릴 수 있다. 따라서 보호는 '벤더 기능'이 아니라 '파일 소유 규칙'(같은 파일은 한 세션만 편집)이어야 한다.
- [2-a UE 5.8 MCP 서버 다중 세션] 로컬 소스(ModelContextProtocolServer.cpp) 확인: Streamable HTTP, `Mcp-Session-Id` 헤더, `initialize`마다 GUID 세션을 Sessions 배열에 추가하고 상한·유휴 만료가 없으며 HTTP DELETE로만 제거된다. 상태 표시줄 괄호 숫자가 세션 수. 즉 Codex와 Claude가 동시에 붙는 것 자체는 허용되고 세션이 섞이지 않는다. 툴 호출은 요청마다 `Tool->RunAsync`이고 서버 대기열은 없다.
- [2-b 직렬화의 실체] FHttpServerModule은 코어 티커(게임 스레드)에서 Tick하며 `check(IsInGameThread())` → 모든 세션의 요청이 게임 스레드에서 도착 순으로 처리된다. 동기 툴(액터·프로퍼티·에셋)은 자연히 직렬이지만, 비동기 툴(StartPIE는 PostPIEStarted 대기, 자동화 테스트)은 완료 전에 다른 세션의 호출이 끼어들 수 있다. Epic 문서의 '겹치는 툴 호출을 내지 말 것'은 클라이언트 의무다. 결론: 서버는 '세션 격리'는 해 주지만 '에디터 상태(PIE·선택·미저장 에셋·라이브 코딩)'는 전역이라 자원 잠금은 클라이언트 쪽에서 해야 한다.
- [2-c 라이브 코딩·PIE 중 타 클라이언트 영향] LiveCodingToolset.CompileLiveCoding은 `Compile(WaitForCompletion)`으로 게임 스레드를 완료까지 점유 → Claude가 라이브 코딩을 돌리는 동안 Codex의 모든 MCP 요청이 응답 없이 대기하고, 클라이언트 측 타임아웃(추정: Codex tool_timeout_sec 기본 60초, Claude MCP_TOOL_TIMEOUT)에 걸리면 Codex는 오류를 받지만 에디터는 계속 실행한다. StartPIE는 에디터 전체를 PIE(Play In Editor, 에디터 내 플레이) 모드로 바꾸므로 Codex의 에셋 편집·저장·재가져오기와 충돌한다. `ue_editor.py restart`(헤더 변경·새 클래스 시 필수, L-build-01)는 프로세스를 종료하므로 Codex의 미저장 에셋·MCP 세션이 사라진다(ue_editor.py stop이 경고하는 이유). 즉 위험 순위: restart > PIE/자동화 테스트 > 라이브 코딩 > 일반 툴 호출.
- [2-d Blender MCP] addon.py는 연결마다 스레드를 만들고 명령을 큐에 넣어 메인 스레드 타이머(50ms)가 하나씩 처리하므로 두 클라이언트를 거부하지 않고 직렬화한다. 저장소 Run-BlenderMCP.ps1은 9876 리스너를 재사용하고 클라이언트마다 stdio 서버를 새로 띄우므로 Claude가 붙어도 오류는 없지만 장면 상태는 공유된다. (가) 시나리오에서는 Codex만 쓰므로 소유 표기 한 줄로 충분하다.
- [3-a 워크트리의 언리얼 비용(2026-09-18 측정)] Content 2.5GB는 워크트리마다 체크아웃 복제(LFS 객체 3.0GB는 .git/lfs/objects 공유라 재다운로드 없음), Intermediate 5.3GB + Binaries 0.95GB는 워크트리마다 전체 재빌드(추정 수십 분), Saved 0.64GB 별도. DDC(Derived Data Cache, 파생 데이터 캐시)는 UE 5.4+ Zen 로컬 캐시 C:\ProgramData\Epic\Zen\Data가 기계 전역이라 중복되지 않는다(선행 조사의 'DDC 중복' 추론은 정정). 에디터를 2개 띄우면 MCP 포트 8000이 충돌하지만 `-ModelContextProtocolPort=N` 오버라이드가 있고, 대신 벤더 MCP 설정 7벌은 추적 파일이라 워크트리별로 다르게 둘 수 없다. UBT(UnrealBuildTool) 전역 뮤텍스 때문에 두 워크트리의 빌드는 어차피 직렬(-WaitMutex). 라이브 코딩 프로세스 그룹은 실행 파일 경로 기준이라 워크트리별로 분리될 것으로 추정(미검증).
- [3-b 워크트리 네이티브 지원] Claude Code `claude -w`는 .claude/worktrees/<name>에 브랜치 격리 체크아웃을 만들고, Codex 0.154.0은 `--worktree`/`/worktree`(실험, `codex features enable worktrees`)를 제공하며 둘 다 '포트·캐시 등 런타임 상태는 격리 안 됨'을 명시한다. 언리얼에서 워크트리가 이득인 유일한 조합은 'Claude=워크트리에서 C++ 전용(Build.bat + UnrealEditor-Cmd 헤드리스 자동화 테스트, 에디터·Content 불가촉), Codex=주 트리에서 에디터 1대 소유'다.
- [3-c 커밋 섞임] `git commit -- <path>`는 `--only`라 그 파일의 작업 트리 전체를 다시 스테이징해 다른 에이전트의 미스테이징 헝크를 흡수한다. 안전한 관례는 (1) 에이전트는 인덱스를 건드리지 않고 사람이 커밋(현행 AGENTS.md 8절과 일치, single-committer 패턴), (2) 커밋 전 `git add -p` 또는 `git add <경로>`로 스테이징하고 pathspec 없는 `git commit`, (3) 커밋 메시지 접두어 `[<agent>]`는 Worklog 항목의 파일 목록과 대조. 자동 WIP 커밋은 같은 트리에서는 다른 에이전트의 파일까지 담기 쉬워 워크트리·브랜치 분리가 있을 때만 의미가 있다.
- [4 2026 도구] Beads v1.3.0(2026-09-15)은 리스(5분 TTL)·heartbeat·reclaim·CAS(Compare-And-Set) 갱신으로 '죽은 세션 청구 회수'를 네이티브로 해결했지만 Dolt·.beads gitignore·20~30 에이전트 설계는 그대로다. TICK.md는 .tick.lock(30초·3회) 단일 파일 보드, Arggon은 Node 22.12+·리스 필드·'같은 트리 동시 에이전트 비대상' 명시, wit는 TS/JS/Python 전용·Bun·유닉스 소켓, mcp-lock-manager는 Node·.locks/·PID 검사(Windows 미기재), mcp-locks는 bash, lockstep-mcp는 inactive. 2-에이전트·Windows·C++·'규칙 우선' 조건에서 그대로 도입할 것은 없고, 빌릴 아이디어는 '리스 TTL + heartbeat + PID 생존 검사 + CAS 청구'다.
- [훅 게이트 가능성] 세 벤더 모두 PreToolUse로 MCP 툴 호출을 가로채 거부할 수 있다(Claude matcher `mcp__unreal-mcp__.*` exit 2/deny, Codex `.codex/hooks.json` matcher `mcp__.*` + permissionDecision deny(비관리 훅은 첫 실행 검토), Antigravity `.agents/hooks.json` PreToolUse `{"decision":"deny"}`). 단 Claude는 MCP 호출에 'ask'가 적용되지 않았다는 미해결 보고(#81569)가 있어 deny도 미검증이므로, 실제 게이트는 저장소 스크립트(`uemcp.py`·`run_in_editor.py`·`ue_editor.py` 진입부의 잠금 검사)에 두고 훅은 2차 방어로만 쓴다.

## 권장하지 않는 것
- **SQLite WAL 장부 정본 + 마크다운 생성(구성 후보로 검토)** — 기술적으로는 로컬 NTFS 2프로세스에 적합하지만, DB 바이너리는 git diff로 검토 불가(사용자 조건), 커밋용 JSONL(JSON Lines) 내보내기와 생성기 유지가 추가되고, 세션당 항목 1~3개·에이전트 2개 규모에서는 msvcrt 잠금 1개 아래 append 스크립트(구성 B ②)와 동일한 결과. 5개 이상 에이전트·질의 필요가 생기면 재검토.

- **TICK.md·Arggon·Hermes kanban·lockstep-mcp(작업 보드 교체형)** — 세 대장(P/M/A~G)을 단일 보드로 바꾸는 이관 비용이 들고, TICK은 런타임·Windows 미기재, Arggon은 Node 22.12+·'같은 트리 동시 에이전트 비대상' 명시, Hermes는 자체 프레임워크 종속, lockstep-mcp는 inactive·macOS/Linux 런처. 담당 필드+리스 규칙으로 같은 효과.

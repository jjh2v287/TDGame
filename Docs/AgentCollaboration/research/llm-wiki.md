# LLM Wiki(Karpathy) 조사

종류: 리서치 · 작성: 2026-09-18 claude · 웹 사실은 URL과 확인 날짜 기준. 결론은 `../../AgentCollaboration_Plan.md` 1절.

## 주제
Andrej Karpathy "LLM Wiki"(2026-04) 원문 구조·한계·커뮤니티 구현 조사와, 다중 코딩 에이전트(Claude Code·Codex·Gemini CLI)가 공유하는 소프트웨어 저장소(TDGame)에 대한 적용성 평가

## 핵심 사실
- 발표 시점: Karpathy가 2026-04-03 X에 워크플로를 올리고 2026-04-04 gist 'llm-wiki.md'(약 12K 단어, 'idea file')를 공개. 2026-09-17 현재 별·포크 각 5,000+ (gist 페이지, VentureBeat 2026-04-03).
- 구조(원문): raw/(불변 원본, 진실의 원천) · wiki/(LLM 전담 작성) · schema 문서(원문이 'CLAUDE.md for Claude Code or AGENTS.md for Codex'라고 명시) 3계층. 필수 파일은 index.md(페이지별 링크+한 줄 요약, 카테고리별)와 log.md(append-only, `## [YYYY-MM-DD] op | Title`). 커뮤니티 표준 레이아웃은 overview.md, sources/, entities/, concepts/, syntheses/ 추가.
- 작업 3종(원문): ingest(1 소스 → 요약 페이지 + 엔티티/개념 페이지 + index + log, 10~15 페이지 수정), query(index로 페이지 찾기 → 인용 포함 답 → 좋은 답은 새 페이지로 환류), lint(모순, 낡은 주장, 고아 페이지, 개념 누락, 상호참조 누락, 데이터 공백 점검).
- RAG(Retrieval-Augmented Generation, 검색 증강 생성)와의 차이: RAG는 질의마다 원본 조각을 다시 찾아 재해석하므로 '누적이 없다'. LLM Wiki는 한 번 컴파일해 두고 유지하므로 지식이 복리로 쌓인다('LLM = 컴파일러, Obsidian = IDE(통합 개발 환경), wiki = 코드베이스'). 핵심 차별점은 '쓰기 루프'(LLM이 자기 출력을 다시 파일함).
- 규모·검색(원문+Karpathy 수치): 약 100 소스·약 40만 단어·수백 페이지까지는 index.md + grep으로 충분, 임베딩 인프라 불필요. 그 이상은 qmd(BM25(Best Match 25, 키워드 순위 함수)+벡터 하이브리드) 같은 검색 보강. 원문 결론: '모든 것은 선택적·모듈식, 도메인에 맞게 취사선택'.
- 권장 도구(원문): Obsidian(그래프 뷰·Dataview·Web Clipper·Marp), Claude Code/OpenCode/Pi 같은 에이전트, qmd, git. 사람 역할은 소스 큐레이션·질문·의미 판단, 'LLM's job is everything else'(요약·상호참조·정리·일관성).
- 알려진 한계 — 환각 고착: LLM이 쓴 오류가 '노트의 한 줄'이 되어 이후 ingest가 그 위에 쌓임(Proudfrog 2026-04-08, Neo4j 2026-08-31, Joi Ito, HN). 같은 모델의 자기 lint는 한계('감사자를 감사'). 커뮤니티 대응은 raw 불변 + git diff/롤백 + 승격 게이트(사람 검토).
- 알려진 한계 — 드리프트/낡음: 원본(코드)이 바뀌어도 위키가 안 바뀌면 '자신 있게 틀린 문맥 = 없는 것보다 나쁨'(Verdent 2026-04-06). 코드베이스 적용 사례는 마지막 커밋 SHA를 인덱스에 저장하고 diff로 영향 페이지만 갱신(yysun 2026-04-12), 또는 CI(지속적 통합)에서 증분 갱신(deepwiki-skill).
- 알려진 한계 — 비용(추정치, 실측 공개 없음): ingest 1건 ≈ 35K 토큰, 100문서 위키 전체 주간 lint ≈ 300K 토큰, 월 $5~50(Proudfrog). Claude Pro에서는 월 4~8회 ingest가 현실적(August Dispatch 2026-05-11). 반면 arXiv 2604.11243은 4쿼리 실험에서 RAG 대비 84.6% 토큰 절감 — 단 소규모·주제 집중 가정.
- 알려진 한계 — 규모: lint의 모순 검사는 N×N 비교(HN), 파일시스템 grep은 위키 크기에 선형(Neo4j), 77페이지쯤부터 index 한 줄 요약이 모호해져 잘못된 페이지 선택(장기 운영 블로그). 범위 지정 없는 '위키 갱신'은 100+페이지에서 토큰 낭비와 미묘한 불일치 유발.
- 알려진 한계 — 사람 의존: '기록해'라고 사람이 말하지 않으면 교훈이 대화에 묻힘. 성공 사례는 입력이 유한한(bounded) 프로젝트 단위. '두 번째 뇌 묘지'(Evernote·Roam·Mem 등) 패턴처럼 유지 부담이 가치를 넘으면 방치됨.
- 결정론 대체 흐름(2026-07 이후 뚜렷): 인덱스 생성·양방향 링크·고아/깨진 링크 lint는 LLM 없이 프로그램으로(Towards Data Science: 5,000파일 12.4초·API 0회; akm: '위키 조작에 무조건적 LLM 호출 없음'; Mograbi CLI: lint 실패 시 exit 1 → pre-commit 훅). LLM은 의미적 연결·모순 판단(약 10%)에만.
- 커뮤니티 구현 규모·평가: 2주 만에 수십 개. SamurAIGPT/llm-wiki-agent 3,500+★(CLAUDE.md/AGENTS.md/GEMINI.md 스키마 3벌 분리), Astro-Han/karpathy-llm-wiki 2.3k★(Agent Skills 표준 SKILL.md 1벌로 Claude Code·Cursor·Codex 지원, 94문서 실운영 후 신선도 해시·신뢰도 점수·벡터·온톨로지를 의도적으로 제외), Obsidian 공식 플러그인, Hermes Agent 번들 스킬, Mograbi/llm-wiki(오프라인 CLI). 다중 에이전트 공유 사례 WUPHF는 draft→promotion 게이트·JSONL 사실 로그·git 작성자 식별을 채택했고, HN 반응은 GIGO(쓰레기 입력 → 쓰레기 출력) 우려가 지배적.
- HN(Hacker News) 반응(296점): '기존 Copilot instruction 파일·어시스턴트 메모리와 중복'이라는 비판과 함께 '코드·문서·ADR(Architecture Decision Record, 아키텍처 결정 기록)·작업 항목을 모두 저장소 안에 표준 형식으로 두라'는 대안이 제시됨 — 소프트웨어 저장소에서는 위키를 따로 두기보다 저장소 자체를 위키로 쓰는 쪽이 자연스럽다는 뜻.
- 에이전트 로더 동작(공식 문서, 2026-09-17 확인): Claude Code는 AGENTS.md를 읽지 않으므로 CLAUDE.md에 `@AGENTS.md` import(Windows는 symlink 대신 import 권장), CLAUDE.md 200줄 이하 권장, @import는 시작 시 전부 로드되어 컨텍스트 절약 없음, `.claude/rules/`의 `paths:` frontmatter로 경로 조건부 로드 가능. Codex는 ~/.codex/AGENTS.md → 프로젝트 루트 → 하위 순으로 이어붙이며 '가까운 파일이 뒤에 와서 앞을 덮어씀', 합계 32KiB 상한. Gemini CLI는 ~/.gemini/GEMINI.md + 워크스페이스 GEMINI.md를 이어붙이고 context.fileName에 AGENTS.md 지정 가능, @import 지원.
- 위 로더 사실의 함의(전제 사실 3의 충돌): 전역 '~/.codex/AGENTS.md'·'~/.gemini/GEMINI.md'의 'AGENTS.md 참고 하지 않는다'는 프로젝트 파일보다 앞에 붙으므로, 프로젝트 AGENTS.md(및 GEMINI.md) 1절에 '전역 지침의 "AGENTS.md 참고하지 않는다"는 이 저장소에서 무효'라고 명시하면 근접 우선 규칙으로 뒤집힐 가능성이 높다. 다만 지침은 강제가 아니므로 확실한 해결은 전역 파일의 해당 줄 삭제. Codex 32KiB 합계 상한 때문에 AGENTS.md(현재 15.8KB, C:\Project\TDGame\AGENTS.md)는 '인덱스'로만 유지하고 위키 본문이 되면 안 된다.
- TDGame 현재 구조 대응: AGENTS.md는 14절(1절 적용 우선순위, 9절 작업 절차 85~106행, 11절 도구, 12·13절 작업 대장 위치). 9절 '작업 전'(89~92행)에는 '어느 인덱스를 읽을지', '작업 후'(103~106행)에는 '어디에 무엇을 기록할지'가 없다. Tools/README.md(9KB)는 0~5절 중 5절 '실측된 함정'(73행)이 교훈 기록 역할을 이미 일부 수행. Docs/Tasks/는 README·decisions·phase-0~4 6파일(약 60KB). Docs/Validation/은 이미지·JSON(원본 증거)과 md(해석)가 한 폴더에 혼재.

## 권장하지 않는 것
- **별도 wiki/ 폴더에 LLM이 코드베이스를 재요약한 엔티티·개념·모듈 페이지를 생성·유지(원문의 wiki 계층을 코드에 그대로 적용, DeepWiki류)** — 소프트웨어 저장소에서는 코드가 이미 진실의 원천이고 Serena·grep으로 직접 읽을 수 있어 요약본은 '정보 손실 + 드리프트'만 추가(Neo4j 2026-08-31, Verdent 2026-04-06: 'API 계약·타입은 코드에'). 코드가 바뀔 때마다 재컴파일 비용(ingest ≈ 35K 토큰/건)이 들고, 낡으면 '자신 있게 틀린 문맥'이 됨. TDGame Docs는 이미 1.09MB라 더 늘리면 index 모호성 문제(77페이지 사례)가 심해짐. 위키에 둘 것은 '왜'(결정·근거·제약·함정)뿐이며 그건 이미 decisions.md·계획서가 담당.
- **모든 세션 대화·조사 결과를 자동 ingest(무조건 환류)** — Proudfrog·August Dispatch 모두 '읽는 것 전부 ingest'는 비용이 이득을 앞지른다고 경고, 성공 조건은 유한한 입력. 사용자는 토큰 절약을 중시. 환류 대상은 '검증된 함정 1줄 + 근거 경로'로 제한.
- **LLM이 수행하는 전체 위키 주간 lint(원문 lint를 그대로)** — 100문서 기준 약 300K 토큰/회 추정, 모순 검사는 N×N, 같은 모델의 자기 검사는 환각을 못 잡음('감사자를 감사'). 구조 검사는 결정론 프로그램으로, 의미 검사는 분기별·범위 지정으로.
- **벡터 검색·qmd·그래프 DB(Neo4j) 등 검색 인프라 도입** — 원문 스스로 '~100 소스, 수백 페이지'까지는 index + grep으로 충분하다고 했고, Astro-Han 실운영(94문서)도 벡터·온톨로지를 의도적으로 제외. TDGame 규모(문서 약 1MB, 도구 약 90개)는 이 범위 안이며 Serena 심볼 검색과 Grep이 이미 있음. Neo4j 글은 벤더 제안.
- **에이전트별 스키마 파일 3벌(CLAUDE.md·AGENTS.md·GEMINI.md에 각각 본문)** — SamurAIGPT 방식이지만 규칙이 세 곳에서 따로 드리프트. 전제 사실 2처럼 GEMINI.md는 이미 진입점이고 Claude Code 공식 문서가 `@AGENTS.md` import를 권장하므로 본문은 AGENTS.md 1벌, 나머지는 2~3줄 진입점이면 충분.
- **'사람은 위키를 직접 편집하지 않는다, LLM 전담' 원칙** — Karpathy 원문의 개인 독서 노트 맥락에서 나온 원칙. TDGame의 결정 기록(Docs/Tasks/decisions.md, 00-decision-record.md)과 할 일 대장은 사람이 결정·검토하는 문서이며, HN 비판(사고 과정 상실)과 WUPHF의 '승격 전 사람 검토'가 반대 근거. 대신 '사람 결정 파일은 사람이 우선, 에이전트는 제안 상태로만 추가'가 맞음.
- **신뢰도 점수·원본 신선도 해시·문서별 검토 타이머·형식 온톨로지 같은 부가 메타데이터 체계** — Astro-Han가 94문서 실운영 후 의도적으로 제외한 항목들. 유지 부담이 가치를 넘으면 방치되는 '두 번째 뇌 묘지' 패턴을 부름. 날짜·근거 경로·상태(확인됨/미검증) 3개 필드로 충분.
- **Obsidian 볼트·플러그인(Dataview, 그래프 뷰) 도입** — 원문의 Obsidian은 사람이 위키를 '읽는 IDE'용. TDGame의 독자는 주로 에이전트이고 사람 1명은 이미 Cursor·VS Code로 마크다운을 봄. Obsidian 전용 문법([[wikilink]], [key::value])은 다른 에이전트·GitHub 렌더링에서 깨지므로 표준 상대 경로 링크를 유지하는 편이 다중 에이전트 호환성에 유리.

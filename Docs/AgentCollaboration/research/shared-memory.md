# 다중 에이전트 공유 지식·메모리 방식 조사

종류: 리서치 · 작성: 2026-09-18 claude · 웹 사실은 URL과 확인 날짜 기준. 결론은 `../../AgentCollaboration_Plan.md` 1절.

## 주제
여러 벤더의 코딩 에이전트(Claude Code, OpenAI Codex, Google Gemini CLI/Antigravity)와 여러 세션이 공유하는 프로젝트 지식·메모리 관리 방식 조사(2025~2026) — "사람 1명 + 파일 기반 CLI 에이전트 3종 + git 저장소" 조건에서의 적합 방식 순위

## 핵심 사실
- [호환성] 2026-09 시점 세 에이전트의 '항상 읽는 파일'은 서로 다르다: Claude Code=CLAUDE.md(계층, `@임포트`), Codex=전역 ~/.codex/AGENTS.md + 저장소 AGENTS.md 체인(연결, 합계 32 KiB 기본, 초과분 조용히 절단), Gemini CLI=전역 ~/.gemini/GEMINI.md + GEMINI.md(연결, `@임포트`, `context.fileName` 배열로 AGENTS.md 추가 가능) / Antigravity=AGENTS.md와 GEMINI.md 모두 읽음(같은 계층 우선순위 미문서화). 출처: code.claude.com/docs/en/memory, learn.chatgpt.com/docs/agent-configuration/agents-md, geminicli.com/docs/cli/gemini-md, thepromptshelf Antigravity 가이드(확인 2026-09-17).
- [변동성] Gemini CLI는 2026-06-18부로 무료·Pro/Ultra 계층에서 Antigravity CLI로 대체됐다(developers.googleblog.com, 2026-05-19 발표). Antigravity CLI는 루트 AGENTS.md와 `.agents/`(skills)를 로드하고 `agy inspect`로 확인할 수 있다. 사용자가 실제로 어느 쪽 바이너리를 쓰는지에 따라 GEMINI.md 경로가 달라지므로 규칙은 AGENTS.md 한 곳에 두는 것이 안전하다.
- [전역 파일 충돌의 실제 동작] Codex는 전역 파일을 먼저, 프로젝트 파일을 나중에 연결하고 '가까운 파일이 충돌 시 우선'이므로 프로젝트 AGENTS.md 내용 자체는 로드된다. 그러나 전역 파일의 'AGENTS.md 참고 하지 않는다'는 지시가 함께 들어가 모델이 임의로 어느 쪽을 택할 수 있고(Claude 문서도 '두 규칙이 모순되면 임의 선택'이라고 명시), 전역 파일 바이트가 32 KiB 예산을 먼저 소모한다. Gemini/Antigravity도 전역 ~/.gemini/GEMINI.md를 항상 참조한다. 이 충돌은 저장소 안에서 고칠 수 없고 사용자가 전역 파일의 해당 줄을 삭제해야 한다.
- [현 저장소 상태] GEMINI.md는 AGENTS.md를 산문으로만 언급(4행)하고 `@AGENTS.md` 임포트가 아니므로 Gemini CLI는 AGENTS.md를 자동 로드하지 않는다. .gemini/settings.json에 context.fileName 없음, .codex/config.toml에 project_doc_max_bytes 없음, 프로젝트 CLAUDE.md 없음(사용자 전역 CLAUDE.md의 산문 지시에 의존). `.agents/`·`.claude/skills/` 디렉터리가 없어 Tools/AnimationAuthoring/SKILL.md, Tools/BlenderAnimation/SKILL.md는 어떤 에이전트의 스킬 탐색 경로에도 잡히지 않는다.
- [크기·내용 근거] ETH Zurich 연구(arXiv 2602.11988, 2026-02): 컨텍스트 파일은 평균 성공률을 올리지 못하고 비용을 20% 이상 올림; 저장소 개요는 무익, 지시문은 잘 따름, 비표준 도구·빌드 명령 같은 '유추 불가 정보'만 넣으라고 권고. GitHub 2,500개 저장소 분석(2025-11-19): 명령(플래그 포함) 먼저, 예시 1개, 항상/물어봄/금지 3단 경계. Claude 문서: 200줄 이하 권장. Codex: 전역+프로젝트 합계 32 KiB(이슈 #13386 미해결). Antigravity 규칙 파일: 12,000자 하드 캡(2차 자료). 현재 AGENTS.md 약 16KB는 Codex 한도 안이지만 Antigravity 캡을 넘을 수 있어 '라우터'로 슬림화가 필요하다.
- [스킬 표준이 사실상의 공용 계층] Agent Skills(SKILL.md)는 Claude Code, Codex, Gemini CLI/Antigravity, Cursor 등 40여 클라이언트가 지원하는 공개 표준이며 점진 공개(시작 시 이름·설명만 약 50~200토큰/스킬, 본문은 활성화 시)로 토큰이 싸다. 디렉터리는 Codex와 Gemini/Antigravity가 `.agents/skills/`(Gemini는 .gemini/skills보다 우선)로 겹치고, Claude Code만 `.claude/skills/`를 본다(공식 문서에 .agents/skills 없음). Windows 심볼릭 링크는 관리자 권한이 필요하므로 복사 동기화 스크립트가 현실적이다.
- [벤더 자동 메모리는 공유 불가·불안정] Claude 자동 메모리는 기계 로컬(~/.claude/projects/…, MEMORY.md 200줄/25KB만 로드)이나 `autoMemoryDirectory`로 위치를 저장소 안으로 옮길 수 있다. Codex 메모리는 ~/.codex/memories/ 사용자별·기본 꺼짐·손편집 비권장이며 공식 문서가 '팀 규칙은 AGENTS.md나 체크인 문서에'라고 명시. Antigravity 지식 항목은 ~/.gemini/antigravity/knowledge/(홈)이고 Windows에서 생성 안 되는 버그 보고(2026-03-04). Cursor Memories는 2.1에서 제거(2025-11). 따라서 세 에이전트가 공유하는 유일한 매체는 저장소 파일이다.
- [Serena는 이미 갖춘 파일 기반 공유 메모리] Serena 메모리는 `.serena/memories/*.md`로 저장소에 커밋되며 Serena MCP를 쓰는 어떤 에이전트든 같은 파일을 읽고 쓴다(공식 문서). 다만 이 세션에서 Serena 연결이 실패했고 저장소의 .serena/에는 logs만 있다. MCP 없이도 마크다운 파일이므로 직접 읽을 수 있으나, 지식 저장소를 두 곳(.serena/memories와 별도 lessons)으로 나누면 중복이 생긴다.
- [메모리 뱅크류의 실패 양상] Cline Memory Bank는 6개 파일을 매 작업 전부 읽게 하여 고정 비용이 크고, 실제 저장소에서 11개 파일이 3개월 이상 방치된 드리프트 사례가 있다(ai-antispam #24). STALE 벤치마크(2026-05): 최상위 모델도 무효화된 메모리 인식·적용 정확도 55.2% → 오래된 메모리는 '검색은 되지만 틀리게 행동'하게 만든다. 완화책은 날짜/검증일 표기, 최근 N건 슬라이딩(temporal memory bank), 스크립트 lint.
- [Karpathy LLM 위키의 적정 범위] 원본 문서(논문·기사)를 LLM이 요약·교차링크하는 패턴이며 코드 저장소 자체가 진실 원천인 상황과는 목적이 다르다. 비용 어림: ingest 1회 약 35k 토큰, 100쪽 lint 약 300k 토큰(proudfrog, 2026-04-08); 150~200쪽 넘으면 인덱스 없이는 중복·링크 품질 저하, 2~3주마다 30~45분 수동 정리(kunalganglani, 2026-04-15). 환각이 위키에 굳어져 lint가 못 잡는 '닫힌 인용 루프' 비판(2차 자료). 가져올 가치가 있는 부분은 index.md(한 줄 목록) + log.md(append-only, 날짜 접두어) + 사람이 diff 검토하는 규율뿐이다.
- [교훈 기록(compound) 패턴의 최소 형태] Every의 Compound Engineering은 docs/solutions/에 YAML 프런트매터 붙은 해결 문서를 쌓고 CLAUDE.md에 재발 방지 규칙을 추가한다. Will Larson(2026-01-19)은 '한 시간이면 도입 가능한 싼 실험'이라 평가하되 병렬 리뷰어는 토큰 과다·명령 이름 변동(2026-08-01 비교 글)이라 1인 개발자는 가벼운 형태부터 권고. 즉 플러그인 도입 없이 '해결 문서 + 인덱스 + AGENTS.md 한 줄 규칙'으로 충분하다.
- [외부 메모리 서비스의 특성] Mem0/Zep/Graphiti/Letta는 서비스+DB(벡터 또는 Neo4j) 기반이며 MCP로 여러 벤더 에이전트에 붙일 수는 있다. 그러나 어느 것도 종합 우위가 없고(8차원 중 3개 이상 승리 없음), git diff로 검토할 수 없으며, OWASP MCP Top 10이 메모리 오염을 위협으로 지목하고 mem0 OpenClaw에 CVE 6건, 노후화·망각 정책은 미해결로 자인. 1인+git 조건에서는 파일이 이미 교차 벤더 공유를 달성하므로 추가 이득이 작다.
- [커밋 추적] Lore(arXiv 2603.15566, 2026-03)는 git 트레일러로 결정·에이전트 정보를 남기자는 제안(실증 없음). 도구 없이 `Agent:`/`Task:` 트레일러만 관례화해도 `git log --format=%(trailers:key=Agent)`로 결정론적 추적이 가능하며, Claude Code는 이미 Co-Authored-By 트레일러를 붙인다.
- [토큰 비용 구조 요약] 항상 로드: CLAUDE.md/AGENTS.md/GEMINI.md 본문 + 임포트 전체(임포트는 절약 아님) + MEMORY.md 상위 200줄 + 스킬 메타데이터(스킬당 50~200토큰) + MCP 도구 정의(서버당 수천~수만 토큰, GitHub MCP 91개 도구 약 46k). 조건부 로드: `.claude/rules` paths 규칙, 하위 디렉터리 CLAUDE.md/GEMINI.md(JIT), 스킬 본문, 링크된 문서. 따라서 '항상 읽는 부분'을 라우터 수준으로 줄이고 나머지는 경로·스킬·문서 링크로 미루는 것이 세 에이전트 공통으로 유효하다.

## TDGame에 적용할 만한 관례
| 관례 | 왜 맞는가 | 비용 | 위험 |
|---|---|---|---|
| 1순위: 루트 AGENTS.md를 '라우터'로 슬림화하고, 각 벤더 진입 파일은 임포트 한 줄로 통일 — CLAUDE.md(프로젝트 루트) = `@AGENTS.md` + Claude 전용 몇 줄; GEMINI.md = `@AGENTS.md`(현재의 산문 언급을 임포트로 교체) + `.gemini/settings.json`에 `"context": {"fileName": ["AGENTS.md","GEMINI.md"]}`; Codex는 자연 탐색. AGENTS.md 내용은 ETH/GitHub 연구대로 '빌드·테스트 명령(플래그 포함), 항상/물어봄/금지 경계, 비유추 함정, 문서·도구·할일대장 위치 인덱스'만 남기고 아키텍처 설명은 Docs/로 이동. 사용자는 전역 ~/.codex/AGENTS.md와 ~/.gemini/GEMINI.md의 'AGENTS.md 참고 하지 않는다' 줄을 삭제. | 요구 (a) '모든 에이전트가 새 세션에 AGENTS.md를 읽는다'를 벤더 기능(임포트·파일명 설정·자연 탐색)으로 보장하는 유일한 방법. 현재는 Claude가 전역 CLAUDE.md 산문에, Gemini가 GEMINI.md 산문에 의존해 실제 로드가 보장되지 않고, Codex는 전역 지시와 충돌 상태. 저장소 안에 CLAUDE.md를 두면 전역 파일 편집 없이도 동작(Windows에서 심볼릭 링크 대신 임포트 권장은 공식 문서). | 토큰: AGENTS.md 슬림화로 매 세션 고정 비용 감소(16KB→목표 200줄 이하, Antigravity 12,000자 캡·Codex 32 KiB 합계 안). 작업: 파일 3개 편집 + settings.json 1줄, 1회성. 유지: 규칙 변경 시 AGENTS.md 한 곳만. | 전역 파일의 상충 지시를 사용자가 지우지 않으면 Codex/Gemini에서 여전히 임의 선택 가능. Antigravity에서 GEMINI.md와 AGENTS.md가 같은 계층에 있을 때 우선순위 미문서화 → GEMINI.md는 임포트 한 줄만 두어 내용 충돌을 원천 차단. Gemini CLI가 Antigravity CLI로 대체되면서 설정 키가 바뀔 수 있으므로 `agy inspect`/`/memory show`로 로드 확인 절차를 AGENTS.md에 적어둘 것. |
| 2순위: 벤더 중립 `.agents/` 디렉터리를 저장소 안 공용 계층으로 채택 — `.agents/skills/<name>/SKILL.md`(Codex·Gemini/Antigravity 공식 탐색 경로, Tools/AnimationAuthoring·BlenderAnimation의 SKILL.md를 여기로 이동 또는 스크립트/자료는 Tools에 두고 SKILL.md만 배치), `.agents/knowledge/`(교훈·함정·결정 인덱스, 아래 3순위), `.agents/memory/`(생성 로그, gitignore). Claude Code용은 `.claude/skills/`에 복사본을 두되 결정론적 동기화 스크립트(Tools/sync_agent_skills.py 같은 것)로 생성. | 요구 (b) '새 도구·리소스를 공통으로 쓸 수 있게 관리'에 부합: SKILL.md는 세 에이전트가 모두 지원하는 공개 표준이고 점진 공개라 항상 비용은 이름·설명뿐. Tools/README 표에 빠진 Animation/AnimationAuthoring/BlenderAnimation 도구와 .gemini/scripts 중복본을 '스킬 1개 = 도구 묶음 1개 + 사용 절차'로 등록하면 README 표와 스킬 설명이 같은 정보를 두 번 유지하는 일을 줄일 수 있음(README는 스킬 목록을 스크립트로 생성). | 토큰: 스킬당 시작 시 약 50~200토큰(Claude) / Codex는 메타데이터 합계 8,000자 상한 — 스킬 10개 이내면 무시 가능. 작업: 디렉터리 생성 + SKILL.md 2개 이동 + 동기화 스크립트 1개(1회 작성). 유지: 새 도구 추가 시 SKILL.md 설명 갱신. | Claude Code가 `.agents/skills`를 공식 지원하지 않아 복사본 이중화 필요(스크립트로 해결, 손편집 금지 규칙 필요). 같은 이름의 스킬이 사용자 전역(~/.agents/skills, ~/.claude/skills)에도 있으면 우선순위 규칙이 벤더마다 달라 혼선 → 프로젝트 스킬 이름에 `td-` 접두어. |
| 3순위: '교훈·함정 기록'을 파일 하나의 인덱스 + 주제 파일로 최소 구현(Karpathy의 index.md+log.md와 Every의 docs/solutions 결합, 위키 전체는 아님) — `.agents/knowledge/INDEX.md`(한 줄 = 날짜 \| 태그 \| 요약 \| 링크, 최신순), `.agents/knowledge/<topic>.md`(프런트매터: verified: YYYY-MM-DD, area: anim\|worldgen\|build, status: valid\|stale), `LOG.md`는 append-only `## [2026-09-17] <agent> \| <제목>`. ## 권장하지 않는 것
- **외부 서비스형 메모리(Mem0, Zep/Graphiti, Letta, Hindsight 등 MCP 메모리 서버)** — 넣지 않기로 한 근거: (1) 공유 문제는 이미 해결됨 — 세 에이전트가 공통으로 읽는 매체는 저장소 파일이며, 서비스 도입은 벤더별 MCP 배선 3벌과 상시 프로세스(벡터 DB 또는 Neo4j)를 추가할 뿐 파일이 못 하는 공유를 제공하지 않음. (2) 검토 불가 — 메모리 내용이 git diff에 나타나지 않아 사용자가 잘못된 기억을 잡아낼 수 없고, STALE 연구(55.2%)와 mem0 자사 블로그가 노후화·망각을 미해결로 인정. (3) 보안 — OWASP MCP Top 10의 메모리 오염 위협, mem0 OpenClaw CVE 6건; 이 저장소는 도구 결과 안의 지시문을 따르지 않는 규칙을 두는데 서비스 메모리는 그 지시문이 다음 세션까지 살아남는 경로가 됨. (4) 토큰·비용 — 매 턴 검색 호출과 주입된 메모리가 고정 비용이 되고, MCP 도구 정의 자체가 수천 토큰(Zylos 연구). (5) 비교 자료가 '어느 것도 종합 우위 없음'이라 선택 근거가 약함. 재검토 조건: 저장소 파일이 수백 개를 넘어 grep으로 못 찾게 되거나 기계 2대 이상에서 동시 작업할 때.
- **Karpathy LLM 위키를 프로젝트 지식 저장소로 전면 도입(raw/ 원본 수집 → LLM이 wiki/ 유지 → LLM lint)** — 목적 불일치: 이 패턴은 외부 원본(논문·기사)의 요약 지식베이스용이고 코드 저장소는 코드·문서 자체가 진실 원천이라 이중 요약이 됨. 비용: ingest 1회 약 35k 토큰, 100쪽 lint 약 300k 토큰, 2~3주마다 30~45분 수동 정리(2026-04 경험담) — 토큰 절약을 중시하는 사용자 조건에 역행. 품질: 환각이 위키에 굳어 자기 인용 루프가 되고 lint가 못 잡는다는 비판. 이미 Docs/가 1.09MB 마크다운 + 인덱스형 계획서 2개로 사실상의 위키 역할을 하므로, 가져올 것은 index.md 한 줄 목록·log.md append-only·사람 diff 검토 규율뿐(3순위에 반영).
- **Cline Memory Bank식 '매 세션 전부 읽는' 다중 파일 메모리(projectbrief/activeContext/progress 등)** — 매 작업 시작에 6개 파일 전부 읽기를 강제해 고정 토큰이 크고, 실제 저장소에서 3개월 이상 방치된 드리프트 사례가 있으며 activeContext/progress가 먼저 읽혀 낡은 전제를 전파. 이 저장소는 할 일 대장(Docs/Tasks 등)이 이미 그 역할이라 중복. 온도 있는 부분(최근 10건 슬라이딩 로그)만 LOG.md 규칙으로 흡수.
- **벤더 자동 메모리(Claude 기본 위치, Codex memories, Antigravity Knowledge Items, Cursor Memories)를 '공유 기록 메모리'로 지정** — 모두 사용자 홈·사용자별이며 공유 불가. Codex는 손편집 비권장·기본 꺼짐·EEA 미제공에 공식 문서가 팀 규칙은 AGENTS.md에 두라고 명시, Antigravity KI는 Windows에서 생성 안 되는 버그(2026-03), Cursor Memories는 2.1에서 제거(2025-11) — 벤더가 언제든 바꾸거나 없앨 수 있음. 개인 편의용으로만 두고 프로젝트 사실은 저장소 파일로.
- **Ruler 같은 '단일 원본 → 벤더별 파일 생성' 도구** — 생성 파일을 gitignore하므로 새 클론·다른 기계에서 `ruler apply`를 잊으면 규칙이 통째로 빠짐. 현재 조건에선 `@AGENTS.md` 임포트 + `context.fileName` 한 줄로 같은 효과를 도구 없이 얻음. 벤더가 5개 이상으로 늘거나 벤더별 규칙 분기가 많아지면 재검토.
- **BMAD / Spec Kit / OpenSpec 같은 스펙 주도 개발(SDD, Spec-Driven Development) 프레임워크 도입** — 지식·메모리 관리가 아니라 개발 프로세스 프레임워크. BMAD는 월 800~2,000달러/개발자 추정에 12+ 페르소나로 토큰 과다, Spec Kit은 그린필드 최적으로 성숙 코드베이스엔 역공학 부담, OpenSpec은 가장 가깝지만 스펙이 자동 갱신되지 않아 Docs/Tasks·decisions.md와 4중 관리가 됨. 필요하면 OpenSpec의 changes/<feature>/{proposal,design,tasks} 폴더 형식만 참고.
- **llms.txt** — 웹 문서 사이트의 크롤러/에이전트용 색인이며 저장소 내부 지식과 무관. 97%가 요청 0건(Ahrefs 2026-05). 'index 한 파일' 아이디어는 3순위 INDEX.md로 충분.
- **ai-memory(akitaonrails)류 훅+SQLite 인덱스 기반 교차 벤더 메모리 도구** — 파일 기반이고 벤더 3종을 지원해 조건에 가장 가깝지만, Rust 바이너리·훅 자동 수집·FTS 인덱스라는 추가 인프라와 Windows 네이티브 '실험 단계'가 부담. 3순위 파일 인덱스가 grep으로 감당 안 될 때의 다음 단계 후보로만 기록.
- **AGENTS.md에 아키텍처 개요·폴더 구조·일반 모범사례를 계속 유지(현재 14절 16KB 형태)** — ETH Zurich 연구: 저장소 개요는 성공률 개선 없이 비용 +20%; 강한 모델일수록 중복 정보를 노이즈로 취급. Codex 32 KiB 합계·Antigravity 12,000자 캡에 걸리면 뒷부분이 조용히 잘려 '지시를 안 따른다'는 오진을 낳음(이슈 #13386). 개요는 Docs/로, 절차는 SKILL.md로, AGENTS.md는 명령·경계·함정·인덱스만.

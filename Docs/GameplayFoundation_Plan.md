# 게임플레이 기반 시스템 계획 — 외부 AI 의견 2건 분석과 TDGame 적용

작성: 2026-11-17 claude(Opus 5.5). 기준은 같은 날 작업 트리(미커밋 포함)이며, 조사는 읽기 전용으로 했다. 구현은 하지 않았다.
입력: 사용자가 가져온 대화 내보내기 2건 — Gemini "워프레임 개발사와 F2P 성공 전략"(2026-11-15~16), ChatGPT "의견 정리"(2026-11-17).
방법: 조사 6갈래(장비·모드, 레벨 생성, 상호작용, 저장, AI·목표·상황 생성, 시험·모듈) + 사실 확인 2갈래(엔진 소스, 웹) → 독립 반박 2개(약 136개 주장 중 25건 정정) → 설계안 3관점(재사용 기반·한 판 완성·비용 위험) → 판정(이 문서) → 계획 반박 2개(둘 다 "고치면 통과", 지적 반영 — 8절). 중간 보고서는 `Saved/AgentOps/20261117/foundation-plan/`(로컬, 커밋 안 됨)에 있다.
관계: 기존 `Docs/Gameplay_Fun_And_Systems_Analysis.md`(2026-10-21, 이하 "기존 분석")를 대체하지 않고 보완한다. 무엇을 만들지(GP 목록)와 큰 순서(기존 분석 7절)는 그 문서를 따른다. 이 문서는 그 가운데 **기반 시스템을 어떻게 재사용 가능하게 만들지**와 **외부 의견의 옳고 그름**을 다룬다.
항목 ID: FD-nn = 기반 시스템 작업, FDQ-nn = 사용자 결정 질문. 기존 ID(D-·GP-·GF-·GQ-·M·MD-·P·F-·G-·FL-)와 겹치지 않음을 검색으로 확인했다.
약어: GAS = 게임플레이 어빌리티 시스템, GE = 게임플레이 효과(Gameplay Effect), ASC = 어빌리티 시스템 컴포넌트, PCG = 절차적 콘텐츠 생성, PIE = 에디터 안 플레이, JSONL = 줄 단위 JSON 기록, F2P = 무료 플레이 + 부분 유료.

## 0. 결론 먼저

**두 문서의 기술 제안은 대부분 TDGame에 이미 있거나(방 조합 던전 생성기·PCG·루멘·동적 내비·결정과 실행이 나뉜 몬스터 AI·월드 상태 저장), 기존 분석이 찾은 빈칸과 그대로 겹친다. 새로 만들 기반 시스템은 다섯 가지다. 상호작용 입구·목표 추적·저장 2판(플레이어 진행)·사건 기록기와 시험 틀 넷은 30분 한 판(수직 단면)이 실제로 부르는 순간에 만들고, 효과 정의(장비·은총 공통 데이터)는 빌드 다양성을 다루는 단계 6에서 만든다. 모두 다음 게임으로 가져갈 수 있는 경계를 지킨다. StateTree 마을 AI·런타임 방 조립·플래티넘식 거래 경제는 받아들이지 않는다.**

- 두 문서가 공통으로 경고한 위험("재미있는 게임 대신 확장성 좋은 틀 만들기")이 이 프로젝트에 이미 수치로 보인다. C++ 약 22.3만 줄 가운데 유체·안개가 약 63%(시험 코드를 빼도 약 52%), 2026-09-01 이후 커밋 298개 가운데 약 절반이 유체·안개이고, 사람이 처음부터 끝까지 플레이한 기록은 0이다. 기술 선택보다 이 배분이 더 큰 결정이다(FDQ-01).
- 그래서 "장르 독립 재사용 시스템을 먼저 연구"하는 별도 단계를 두지 않는다. 대신 한 판에 필요한 기반 시스템을 **계약(인터페이스·데이터 정의·메시지)부터** 만들고, 자동 시험 월드의 맨 폰으로 "게임 전용 코드 없이도 도는가"를 바로 확인하며, 게임 안 사용처가 셋이 되면 API를 확정한다. ChatGPT가 말한 "첫 게임은 필요한 만큼, 둘째에서 공통 발견, 셋째에서 API 확정"을 프로젝트 하나 안에서 싸게 실행하는 방법이다.
- 외부 문서에서 그대로 쓰면 안 되는 기술 오류가 몇 개 있다: Gemini의 방 정렬 식(180도 뒤집기와 언리얼 곱셈 순서 누락), 팩 레벨 액터를 방 단위로 쓰는 안, ChatGPT의 "WaitGameplayEvent는 버스가 아니다"(맞지만 GAS 트리거로 같은 일을 하는 표준 경로를 빠뜨림). 1-2·1-3절에 정리했다.

## 1. 두 문서 분석

### 1-1. 두 문서가 함께 맞힌 것 (TDGame에도 그대로 해당)

1. **데이터 주도 설계와 방 조합(절차 생성)은 서로 다른 축이다.** 하나는 게임 규칙을 코드에서 떼어 내는 방법이고, 다른 하나는 공간을 만드는 방법이다. 둘 다 도입할 필요는 없다.
2. **재미를 먼저 확인하고 틀은 나중에.** Gemini도 "빈 맵에서 전투·빌드 조합이 성립하는지 먼저"를 권했고, ChatGPT는 이것을 가장 중요한 문장으로 꼽았다. 기존 분석의 결론("놓기·보상·강해짐·저장 네 고리를 닫는 30분 한 판부터")과 같다.
3. **워프레임 성공은 그대로 옮길 수 없다.** 수십 명 규모·자체 엔진·기존 팬층을 가진 스튜디오가 몇 년에 걸쳐 살아남은 한 사례다(생존자 편향).

### 1-3. ChatGPT 문서: 맞는 것, 틀린 것, 빠진 것

**첫 답(Gemini 비평)** 은 대부분 정확하다. 팩 레벨과 레벨 인스턴스 구분, PCG 런타임 생성은 트리거·범위 설계가 따로 필요하다는 점(트리거는 GenerateOnLoad 기본·GenerateOnDemand·GenerateAtRuntime, `PCGComponent.h:77-82`), 전투에 영향 주는 엄폐물은 규칙으로 놓으라는 점, 동적 내비 갱신 비용(대안: 내비게이션 인보커·DynamicModifiersOnly), "N×M은 기하급수가 아니다", 손익분기 시점 미검증, 스팀 얼리 액세스를 크라우드펀딩으로 쓰지 말라는 규정까지 확인됐다.

틀리거나 빠진 것:
- **"WaitGameplayEvent는 범용 이벤트 버스가 아니다"** — 사실이지만 절반이다. 트리거 데이터로 부여된 어빌리티는 이벤트에 자동 활성화되고, 어빌리티 밖에서 쓰는 `AbilityAsync_WaitGameplayEvent`도 따로 있다.
- **"UDataValidator"** — 엔진에서 확인되지 않는 이름이다. 실제 확장점은 `UObject::IsDataValid(FDataValidationContext&) const`(`Object.h:1092`)와 `UEditorValidatorBase`다.
- **"GAS는 필요할 때 도입"** — 일반론은 맞지만 TDGame은 이미 GAS(단일 ASC `UTDCombatComponent`) 위에 서 있어 해당 없다.
- **"첫 시제품은 ARoomActor로"** — TDGame 던전은 이미 생성기·검증기가 있어 해당 없다.

## 4. 만들 기반 시스템과 방법

모든 기반 시스템에 공통으로 적용하는 원칙:
- **계약을 먼저, 기능은 한 판이 부르는 만큼만.** 장르 독립 계약(인터페이스·데이터 정의·메시지 구조체)과 TDGame 전용 부분(입력 묶기·HUD·성소·아레나 같은 구체 액터)을 파일 단위로 나눈다.
- **이식성을 바로 확인한다.** 모든 기반 시스템은 자동 시험 월드에서 `ATDGameCharacter`가 아닌 맨 `APawn`으로 동작해야 한다. "다른 게임에서도 쓸 수 있나"의 가장 싼 확인이다. 이 시험은 사용처 수에 넣지 않는다(FD-01 등급은 게임 안 소비자만 센다).
- **사건은 이미 있는 GameplayMessageRouter 통로로.** 새 이벤트 버스를 만들지 않는다. 기반 코드의 메시지·태그는 `Foundation/` 안에 새로 두고, TDGame 메시지(`Core/`)와는 TDGame 쪽 어댑터로 잇는다.
- **로직은 C++, 에셋은 비동기, 난수는 시드 스트림.** (AGENTS.md 7절·OP-33·13절)

### FD-01 경계 규칙과 검사 도구

- 무엇: 기반 시스템 코드가 게임 전용 코드(캐릭터·플레이어 컨트롤러·전투·몬스터 AI·HUD)를 끌어오지 않게 막는 규칙과, 그것을 매번 자동으로 검사하는 스크립트.
- 왜: 재사용성은 나중에 떼어 낼 때가 아니라 매일 지켜질 때 생긴다. 새 모듈을 만들면 컴파일러가 막아 주지만 에디터 재시작·빌드 비용이 들고, 지금은 사용처가 하나뿐이다(6절 과설계 금지).
- 방법(FDQ-02 (a) 승인 시): 기반 코드는 `Source/TDGame/Foundation/{Interaction,Objectives,Recording}/`에 둔다(저장 골격은 지금 위치 `World/Persistence/` 유지). 규칙은 하나다: **기반 계약은 TDGame 전용 타입을 인자·멤버로 쓰지 않는다**(폰은 `APawn`, 대상은 `AActor`). `Tools/check_foundation_boundary.py`가 이 폴더의 `#include`를 끝까지(간접 포함까지) 따라가, 허용 목록(엔진·`Foundation/` 안·GameplayMessageRuntime) 밖을 보고한다. **`Core/`도 허용하지 않는다** — `Core/TDGameplayMessages.h`가 `Combat/Damage/TDDamageTypes.h`를 포함해 전투 코드가 딸려 온다. TDGame 메시지·태그와 잇는 어댑터는 `Foundation/` 밖(`Framework/`·`Combat/`)에 둔다. 처음에는 보고 모드로 기준선을 잰 뒤 실패 모드로 바꾼다. 검사 도구는 간접 포함을 포함한 fixture 폴더로 거짓 음성·양성을 반박 검사한 뒤 등록한다. 영역별 커밋·줄 수 비율을 주 1회 집계하는 작은 스크립트도 같이 만든다(4절 틀 몰두 방지).
- 소비자 수 등급으로 "셋째 사용처에서 API 확정"을 실행한다: 사용처 1개 = 내부(마음대로 바꿈), 2개 = 후보(바꿀 때 두 곳 함께), 3개 = 확정(바꾸려면 결정 기록). 계약마다 만들 때부터 실제 소비자가 1개 이상 있어야 한다.

### FD-02 상호작용 입구 (GP-17)

- 무엇: 상자 열기·성소 활성화·제단 보상 고르기·지름길 열기를 하나의 입구로. 플레이어 F 키, 걸어 들어가기(겹침), 동료, 자동 시험이 모두 같은 함수를 부른다.
- 장르 독립 계약: `ITDInteractable`(C++ 전용 인터페이스, `ITDPersistentActor`와 같은 형식) — `CanInteract(Context)`가 실패 사유를 돌려주고, `Interact(Context)`가 실행하고, 안내 문구를 준다. `FTDInteractionContext`(요청한 폰, 대상, 요청 출처 태그: 입력·겹침·AI·시험), `ETDInteractionResult`(성공·범위 밖·이미 사용·조건 부족·잘못된 대상). 단일 입구 `TryInteract(APawn*, AActor*, 출처)`가 검사 → 실행 → `FTDInteractionCompletedMessage`(요청자, 대상, 대상 종류 태그, 대상 영속 ID) 방송까지 한다. 대상 종류 태그와 영속 ID는 목표·저장이 듣기 위해 처음부터 넣는다. 영속 ID는 `ITDInteractable`이 `FGuid`로 돌려주고, 기반 코드는 `UTDPersistentStateComponent`를 직접 참조하지 않는다. 메시지 구조체와 태그는 `Foundation/` 안에 둔다.
- TDGame 전용: F 입력 묶기와 틱 없는 겹침 구 대상 찾기(`TDGamePlayerController`), 안내 문구 한 줄(기존 C++ 오버레이), 구체 대상(시험 상자, 성소, 제단). 입력 액션·매핑 에셋은 기존 도구 `Tools/Combat/editor_make_combat_assets.py`로 만들고(.uasset이므로 LFS 확인), 묶기는 구르기와 같은 비동기 방식(`TDGamePlayerController.cpp:43-44, 531-581`)을 따른다.
- 첫 단계: 타입·단위 시험 → 시험 상자를 이 입구로 옮김(기존 Exec `Open()`은 입구를 부르는 얇은 포장으로 남김) → 기존 저장 왕복 시험 재실행 → F 입력과 대상 찾기 → 성소(GP-08)가 겹침 출처로 같은 입구를 쓰는지 확인. 제단(GP-16)은 단계 4에서 붙인다.
- 완료 판정: 시험 상자 2개를 콘솔 없이 F로 열고 저장·복원 뒤 같은 상태, 입력과 시험이 같은 입구를 거침, 실패 사유별 시험, 메시지 수신 시험, 맨 폰 시험 월드 통과, 동기 로드 검사·경계 검사 통과.
- 하지 말 것: 몬스터 실행기와 합치기, 행동 태그 `switch`, 별도 실행기 컴포넌트, 서버 권한 코드, 던전 입구·승강기에 F 강제(걸어서 이어짐이 우선).
- 순서 변경 제안(FDQ-03): 기존 분석은 GP-17을 단계 4에 두었지만 크기가 작고 성소(단계 2)·제단(단계 4)·상자가 모두 쓰므로 입구는 단계 2 첫머리로 앞당긴다. 단계 2에서 F 키를 쓰는 소비자는 시험 상자뿐이고, 성소는 걸어 들어가기(겹침 출처)로 같은 입구를 쓴다.

### FD-03 목표 추적 (GP-10)

- 무엇: "지금 무엇을 하면 되는지" 한 줄과 방향 표시, 끝나면 결과 화면. 그 뒷단은 사건을 듣고 진행을 세는 시스템이다.
- 장르 독립 계약: `UTDObjectiveDefinition`(데이터 에셋, 단계 목록) — 단계마다 조건 목록(모두 충족). 조건은 두 종류만: **사건 횟수**(메시지 태그 + 대상 태그나 영속 ID 거르개 + 필요 횟수 — 조우 끝·보스 처치·N마리 처치·상호작용 완료를 모두 덮는다)와 **지점 도착**(태그 붙은 볼륨). `UTDObjectiveSubsystem`(월드 서브시스템)이 메시지를 듣고 카운터(이름 → 정수 표)를 올리고 `FTDObjectiveChangedMessage`를 방송한다. 시스템은 사건을 듣고 평가만 한다 — 적을 죽이거나 문을 열지 않는다.
- TDGame 전용: 목표 데이터 6단계(첫 판은 3단계로 시작해도 된다), 목표 줄·가장자리 화살표(기존 C++ 오버레이 확장), 결과 화면(방식은 GQ-21 결정 뒤). 지점 도착을 알릴 작은 볼륨 액터가 하나 필요하다(지금 메시지 9종에 지역 진입 사건이 없다). 목표 정의 에셋은 에디터 파이썬·언리얼 MCP로 만들고, 시작 전에 `FStreamableManager`로 미리 요청한다.
- 수명·저장: 목표 서브시스템은 월드 서브시스템이다. 시작할 때 진행 기록에서 복원하고, 저장 직전에 진행(목표 ID·단계·카운터)을 FD-04의 진행 기록에 쓴다.
- 완료 판정(단계 2): 아레나 승리만으로 목표가 넘어감, 자동 시험 3개(사건 횟수·지점 도착·진행 기록 왕복), 맨 폰 시험 월드 통과. 재시작 뒤 복원(이어하기)과 사람 기준(처음 하는 사람 3~5명이 질문 없이 도달, 방황 시간 중앙값 90초 이하)은 단계 3 관문에서 본다.
- 하지 말 것: 중첩 조건 트리, 분기 퀘스트·대화, 스크립트 언어, 블루프린트 로직.

### FD-04 저장 2판: 플레이어 진행·자동 저장·이어하기 (GP-08·09)

- 무엇: 껐다 켜도 레벨·주문·물약·목표가 남고, 성소에 닿으면 자동 저장되고, 실행하면 마지막 성소에서 바로 이어진다.
- 있는 것 재사용: 안정 ID 컴포넌트·월드 상태 서브시스템·저장 객체·변환 표·스트리밍 재적용·PIE 시험 틀.
- 더할 것(순서대로, 1~3은 단계 2, 4는 단계 3):
  1. `FTDPlayerProgress` 기록과 저장 2판, 변환 v1→v2. 시험 `MigratesV1`·`RoundTrip`. 진행 값은 GP-05·06·07·14가 만들고 저장은 읽기·쓰기 창구만 둔다. 필드는 그 항목들의 명세가 나온 뒤 확정한다.
  2. 안전한 저장(성소 자동 저장 앞에): `AsyncSaveGameToSlot`은 직렬화(`SaveGameToMemory`)를 게임 스레드에서 하고 파일 쓰기만 다른 스레드에서 한다. 그래서 상태 수집 + 직렬화 구간을 `FPlatformTime`·프로파일 범위로 재고, 실제 월드 저장 20회의 최댓값이 5ms 미만이면 통과로 한다. 슬롯 이름 바꾸기 API가 없으니 슬롯 두 개를 번갈아 쓰고 머리말에 저장 번호·검사값을 둬서 가장 최근의 유효 슬롯을 읽는다. 둘 다 깨졌으면 새 게임.
  3. 성소(GP-08): 부활 지점·물약 충전·자동 저장. 아레나가 시작할 때 체크포인트 칸 하나를 덮어쓰는 잠재 결함(`TDArenaEncounter.cpp:187`)을 성소 칸과 조우 칸 분리로 고친다. 시험 `ShrineSurvivesArenaVictory`.
  4. 시작 시 이어하기·새 게임(새 게임 초기화 `ClearAllState` 호출이 지금 0). 이어하기는 마을을 거치거나 페이드 순간이동하지 않고 마지막 성소에 바로 스폰한다. 시작 로딩 동안 성소 위치를 스트리밍 기준점으로 두고 셀 로드가 끝난 뒤 조종을 넘긴다(`TDSeamlessTravelSubsystem` 재사용 여부는 착수 때 확인).
  5. 필요해질 때만: 기록 단위 버전, 런타임 생성 객체 ID, 제거 기록(묘비).
- 장르 독립 부분: 액터 상태 기록·버전 변환·비동기 슬롯 입출력. TDGame 전용 부분: 진행 기록 내용·던전 상태. 두 부분을 같은 저장 객체 안에서도 구조체로 나눈다.
- 완료 판정: 위 시험 3개, 승리 → 종료 → 재실행에 진행 유지, 저장 끊김 측정값 기록.
- 하지 말 것: 몬스터·투사체 저장, 범용 저장 틀 새로 짜기, 저장 객체 추가, 던전 시드 런타임 재생성(던전은 에디터 굽기라 완료·상자 상태만 저장하면 된다), 동기 로드.

### FD-05 사건 기록기·기반 시험 월드·데이터 검증 (GP-13 + 시험 틀)

- 무엇: 한 판을 하면 무슨 일이 언제 일어났는지(피해·처치·조우·상호작용·목표·저장)가 JSONL 파일로 남고, 도구가 요약 표를 만든다. 재미 측정의 자이자, 버그가 났을 때 상황을 다시 짜 맞추는 기록이다(완전한 재생이 목표는 아니다 — 물리·비동기 때문에).
- 방법:
  1. 선행(몬스터 AI 대장 M0 항목을 청구): M0-01(전투 시험 28개 기준선) → M0-02(피해 문맥에 난수 스트림을 싣고 치명·산개 2곳 교체, 피해 공식 `TDDamageFormula::Compute` 분리, 28개 통과) → M0-07(전역 난수 금지 자동 시험을 Combat·MonsterAI·CombatSim으로). NPC 틱 분산 1곳은 게임 결과와 무관해 범위 밖이다.
  2. 기록 형식·위치는 기존 측정 규격(`Docs/MonsterAI_CombatSim/06-beyond-the-ask.md:35,160-166`: 세션 머리줄, 필드 t·ev·src·dst·amount·ability, `Saved/Telemetry/`)을 따르고 상호작용·목표·저장을 ev 종류로 더한다. 기록기 본체 `UTDGameplayRecorderSubsystem`(게임 인스턴스 서브시스템, 게임·PIE 월드만 기록)은 기반 폴더에 두고 채널·시각·JSON 한 줄만 받는다. 메시지 9종을 JSON으로 바꾸는 어댑터는 TDGame 쪽에 둔다(라우터의 형식 없는 등록 함수는 공개되어 있지 않다). 요약은 `Tools/` 파이썬 도구(한 번 만들어 매번 결정론적으로 실행, 규격에 적힌 요약 도구는 아직 없다).
  3. 자동 전투원 모드(칼만·칼+주문·주문 난사 + 물약, GP-13)를 단계 1 끝, 수치를 바꾸기 전에 붙이고 변경 전 기준선을 기록한다.
  4. 기반 시험 월드: 시험 파일마다 따로 있는 시험 월드 구조체가 12개 이상이고, 몬스터 AI 대장 M0-05가 전투 픽스처를 공용 헤더로 승격할 예정이다(선행 M0-03). 공용 월드가 둘 생기지 않게 M0-05 승격본에 맨 시험 폰(`ATDTestProbePawn`) 구성만 더한다. M0-05 전에는 기반 시험 전용 최소 월드만 두고 M0-05 때 합친다(위치·이름은 M 대장과 맞춘다). 메시지 서브시스템이 게임 인스턴스를 요구하므로 시험 월드는 게임 인스턴스를 만든다. 기존 시험의 대규모 정리는 하지 않는다.
  5. 시나리오 시험: 상호작용 → 저장 → 복원 같은 여러 시스템을 가로지르는 시험(기존 상자 스트리밍 시험을 넓힌다).
  6. 데이터 검증: 목표·효과 정의에 `IsDataValid`, 저장 ID 중복은 사용처가 늘 때 `UEditorValidatorBase` 검사기로.
- 완료 판정: PIE 1회 → JSONL → 요약 표 자동, 같은 JSONL을 두 번 요약하면 결과가 같음, 자동 시나리오(맨 폰 시험)를 두 번 돌리면 사건 수가 같음, 자동 전투원 두 번의 요약 차이 ±10% 이내, M0-07 초록, 기반 시험 월드를 쓰는 시험 3개 이상. 사람 플레이끼리의 비교는 판정에 쓰지 않는다.
- 하지 말 것: Game Features·Spec 형식 도입, 결정론 재생기 본체, 유체 시험 추가.

### FD-06 효과 정의: 장비·은총·유니크 공통 데이터 (GP-27·28 단계 6, GP-16·50은 뒤에 같은 정의)

- 무엇: "도탄", "처치 시 연쇄 번개", "최대 체력 +20" 같은 효과를 데이터 하나로 정의하고, 장비 칸·시련 은총·고정 유니크가 같은 정의를 쓴다(GQ-03 권장 (c)). 첫 소비자는 GP-27·28(단계 6)이다. 보상 제단(GP-16)은 단계 4에 주문·물약 카드로 먼저 열리고 단계 6부터 같은 정의를 쓰며, 고정 유니크(GP-50)는 단계 7이다.
- 방법(Gemini 안을 TDGame에 맞게 고친 것):
  - 능력치 변경: 단일 ASC에 무한 지속 GE를 SetByCaller 수치로 부여하고 핸들로 해제한다. 체력 보너스는 Health가 아니라 MaxHealth.
  - 행동 변형: **피해 규칙 엔진**(사건 8종 × 행동 5종)을 쓴다. 지금 규칙은 피해·상태 정의, 피해 엔티티, 행동 데이터에만 붙으므로, 착용자 규칙 목록을 전투 컴포넌트에 두고 피해 서브시스템이 규칙을 평가할 때 덧붙이는 지점을 새로 만든다. 덧붙인 규칙은 원래 피해 문맥(`FTDDamageContext`)을 이어받아 실행해야 예산(2048/128)·처치 연쇄 깊이(32)가 적용된다 — 새 문맥을 만들면 예산이 새로 생겨 재귀를 못 막는다. 처치 경로는 지금 게임 사용이 0이니 재귀 0·예산 중단 시험을 먼저 두고, 시뮬과 같은 스텝 코드이므로 결정론 시험을 함께 둔다. 기존 분석 GP-27은 "능력이 직접 부른다"였는데, 예산 장치와 결정론 시뮬을 그대로 쓰려고 규칙 엔진 쪽으로 바꿨다. GAS 트리거 어빌리티는 새 능동 기술이 필요할 때만 쓴다.
  - 데이터: `UTDEffectDefinition`(데이터 에셋, 표시 에셋은 소프트 참조 비동기). 대량 표가 필요해지면 몬스터처럼 JSON.
  - 추첨(드롭·보상 제시)은 시드 스트림(M0-02 선행).
- 첫 단계: 효과 2~3종으로 장착·해제·저장 왕복을 닫은 뒤 12종(GP-27).
- 완료 판정: 장착·해제 후 능력치 원복 시험, 재귀 0·예산 중단 시험, 사람 판정 "다른 선택 3회 중 2회 다르게 느껴짐", 효과별 처치 시간 0.85~1.25배(기존 분석 수치).
- 하지 말 것: 모드마다 GE 에셋 대량 생성, 무작위 수치 접사 수프, 인벤토리 화면 먼저, Health 지속 수정자, 범용 이벤트 버스.

### FD-07 (미룸) 상황 생성 = 조우 세트 확장 (GP-33·35, 단계 7)

### 일하는 방식

- 항목마다: 세션(Opus)이 목표·완료 판정·명세를 쓴다 → 보통 구현은 Sonnet 빌더, C++ 설계가 큰 것(FD-06)은 Opus → 독립 반박(Opus) → 사람이 PIE로 손맛 판정이 필요한 것만 확인. 모델 배정은 CLAUDE.md "서브에이전트 운용" 절(Claude 전용)을 따른다.
- 같은 파일을 고치는 빌더는 한 번에 하나(기존 분석 7절 묶음: `TDGamePlayerController`·`TDArenaEncounter`·진행·저장). 새 클래스는 에디터 재시작이 필요하니(L-build-01) 한 단계의 새 클래스를 모아 한 번에 재시작하고, 유체·안개 세션과 빌드 창을 보류 파일로 나눠 쓴다.
- 관문 규칙: 단계 관문(사람이 손으로 플레이한 기록 + JSONL 요약)을 통과하기 전에는 다음 단계의 새 클래스를 만들지 않는다. 미달이면 결함부터 고친다.
- 틀 몰두 방지: 계약 파일(= `Foundation/`의 공개 헤더)은 첫 2주 동안 3개 이하로 두고, 같은 기간에 한 판 몸통(GP-02·03)이 착수되지 않았으면 계약 작업을 멈춘다. 영역별 커밋·줄 수 비율 집계 스크립트(FD-01과 함께 만들어 `Tools/README.md`에 등록)로 FDQ-01 결정이 지켜지는지 주 1회 본다.
- 착수 전 사실 확인 1회: 이 문서의 줄 번호·상태는 2026-11-17 기준이다. 항목을 시작할 때 관련 줄을 한 번 다시 연다.
- 대장: 이 문서의 FD 항목과 기존 분석의 GP 항목을 한 대장으로 등록하는 것은 사용자 승인 뒤에 한다(FDQ-02).

## 6. 사용자 결정 질문

각 질문은 "무엇이 달라지나 · 고를 수 있는 것 · 권장 · 답이 없으면" 순서다.

**[6-1] 유체·안개 연구와 게임 작업의 시간 배분 (FDQ-01)**
- 무엇이 달라지나: 한 판이 언제 손으로 해 볼 수 있는 상태가 되느냐. 지금은 코드의 약 63%·최근 커밋 절반이 유체·안개이고, 한 판 항목(GP)은 10-21 이후 착수 전이다.
- 선택지: (a) 진행 중인 3D 안개 구간(바람 섞기 새 식의 GPU 반영·켬끔 대조·비교 그림·독립 반박)을 닫은 뒤, 한 판 단계 3(보스와 저장)까지 약 6~8주 게임 작업 우선. 유체·안개는 막힘 수정과 게임 연결만 한다(기존 분석 11-5의 연결 작업 — 기록기 공용·업화의 눈 켬끔 판정 — 은 FD-05 기록기와 같은 형식이면 함께 한다). `Docs/NOW.md` 다음 행동 3개 중 2개는 한 판 작업 (b) 게임 7 : 연구 3 (c) 지금처럼.
- 권장: (a), 2주 뒤 단계 1 관문에서 다시 판단. 두 외부 문서와 기존 분석이 같은 결론이고, 유체 투자도 게임에 놓여야 회수된다(GP-44).
- 답이 없으면: 지금 흐름(안개 작업)을 유지하고 이 계획은 대기.

**[6-2] 기반 코드 폴더와 대장 등록 (FDQ-02)**
- 무엇이 달라지나: 재사용할 코드가 한 폴더에 모이고 검사 도구가 경계를 지킨다. AGENTS.md 14절 폴더 목록에 `Foundation/` 한 줄, 15절 대장 표에 "게임플레이(GP·FD)" 한 줄이 늘어난다. 대장은 승인 대기 [1-13](게임플레이 항목 등록)과 같은 대장이다. 절차: decisions.md D-65(제안) → 사용자 승인 → 14·15절 수정.
- 선택지: (a) `Source/TDGame/Foundation/` + 검사 도구, 대장 1개 신설 (b) 기존 폴더(Framework 등)에 흩어 두기 (c) 지금 새 모듈 `TDGameplayFoundation`.
- 권장: (a). (c)는 사용처가 둘 이상일 때.
- 답이 없으면: (b)로 시작하고 검사 도구 없이 진행(나중에 옮기는 비용 증가).

**[6-3] 상호작용(F 키)을 단계 2로 앞당기기 (FDQ-03)**
- 무엇이 달라지나: 성소·상자가 처음부터 같은 입구를 쓰고, 제단(단계 4)도 그대로 붙는다. 단계 2에서 F 키를 쓰는 것은 시험 상자뿐이고 성소는 걸어 들어가면 켜진다. 단계 2가 2~3일 늘고 단계 4가 그만큼 준다.
- 권장: 앞당긴다. 답이 없으면 기존 순서(단계 4)대로 하고, 성소는 걸어 들어가기 전용으로 먼저 만든다.

**[6-4] 사업 모델 가정 (FDQ-04, GQ-22와 묶음)**
- 무엇이 달라지나: 싱글 유료 패키지면 서버·거래·부정 결제 대응이 필요 없고, 지금 구조(복제 0)를 그대로 쓴다. F2P면 서버 권한·경제·운영이 먼저 필요해 계획 전체가 바뀐다.
- 권장: 싱글 유료 패키지 가정, 스팀 페이지 전에 다시 본다. 파운더스식 선판매는 팬층이 생긴 뒤의 이야기이고, 스팀 규정상 "지금 있는 것"을 팔아야 한다.
- 답이 없으면: 싱글 유료 가정으로 진행.

**[6-5] 마을 NPC가 필요해질 때의 AI 방식 (FDQ-05, 지금 결정 불필요)**
- 무엇이 달라지나: 마을 주민 일과(서 있기·걷기·작업대 사용)를 무엇으로 만드나. StateTree는 결정 D4(전투 코어에서 배제)와 D44(NPC를 포함한 모든 캐릭터에 "StateTree는 쓰지 않는다", AGENTS.md 7절도 같은 문구)에 걸린다. D44 문장은 애니메이션 구성 문맥이지만 범위 한정이 없어, 비전투 AI까지 금지하는지는 해석이 갈린다.
- 선택지: (a) 몬스터와 같은 C++ 유틸리티 방식 — 지금 규칙 안 (b) StateTree — 사용자가 D44·7절의 해석을 정하거나 예외를 결정 기록에 남겨야 한다(규칙 편차) (c) Smart Objects 슬롯 + (a) — 금지는 없지만 꺼진 플러그인을 켜야 하고 도입 근거가 필요하다.
- 권장: 거점(GP-36) 착수 때 결정, 그 전까지 (a)를 기본값으로.

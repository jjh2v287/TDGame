## 0. 결론

- **가능하다. 수준 A(무한 생성)는 엔진 내장 부품만으로, 실험 기능 없이, 원점 재설정 없이 만든다.** 막는 엔진 제약 세 가지(월드 파티션 런타임 셀 생성 불가, 랜드스케이프 런타임 생성 불가, 런타임 스폰 액터의 공간 로딩 불가)는 모두 "월드 파티션 밖에 자체 청크 스트리머를 둔다"는 한 가지 결정으로 동시에 우회된다.
- 형태: 지금의 약 1.5 km² 허브(LV_DarkFantasy_OpenWorld, 랜드스케이프 + 월드 파티션)는 그대로 두고, 허브 테두리를 열어 그 밖을 **64 m 정사각 청크**로 끝없이 잇는다. 청크는 C++ 서브시스템 `UTDChunkStreamingSubsystem`이 작업 스레드에서 순수 함수 생성기로 데이터를 만들고, 게임 스레드에서 시간 분할로 풀링된 청크 액터(런타임 메시 지형 + 메시 종류별 ISM)에 붙인다.
- 기술 핵심 결정 다섯 가지:
  1. 생성기 정체성 경로는 **정수 고정소수점 C++**(새 런타임 모듈 `TDChunkGen`). `/fp:fast`(Game)와 `/fp:precise`(Editor) 차이 위험을 설계로 없앤다.
  2. 산포는 **PCG를 쓰지 않고 자체 C++**. 안정 ID·D-47·몬스터 길찾기 입력을 한 데이터에서 얻는다.
  3. 세트피스는 월드 애셋 스트리밍(실험) 대신 **에디터에서 구운 데이터 프리팹**을 같은 ISM·풀 경로로 놓는다.
  4. 몬스터 길찾기(M3-04)는 Recast가 아니라 **청크 보행 격자 위 창 플로우 필드**. 내비메시는 플레이어 클릭 이동 전용으로 줄인다.
  5. 저장은 **영역 파일(32×32 청크) + 청크 차분 + 생성기 버전 동결 + 3단계 교체 쓰기**.
- 순서: A(무한 생성) → B(설치·철거·건물, A 위에 청크 차분) → C(2.5차원 높이 편집, 청크 높이 차분). 첫 관문 G0는 시험 맵에서 1~2주(약 9~10 작업일)에 판정한다.

### 2.2 좌표·정밀도 규약

- 위치는 double(엔진 그대로), 청크 색인은 int64 `floor(위치cm / 6400)`, 생성기 내부 표본 위치는 **int64 정수 cm**. 격자 내부 비율만 고정소수점으로 바꾼다(프로토가 float64로 증명한 "정수 나머지를 작게 만든 뒤에만 실수로" 원칙의 정수판, `chunkgen.py:139-146`) [검증 원칙, 정수판은 추정].
- 원점 재설정은 쓰지 않는다. Chaos·Mover·월드 파티션이 원점 이동과 맞지 않는다(`S1:01-engine-precision.md`: `PhysScene_Chaos.cpp:2262-2270`, `MoverComponent.cpp:965-991`) [검증·일부 추정].
- 컴포넌트 원점 규칙: 렌더·인스턴스 변환이 float 상대값이 되는 모든 것(지형 메시, ISM, 나이아가라)은 **원점을 자기 청크(또는 512 m 지역) 원점에 둔다.** 그래야 ±1,000 km에서도 국소 오프셋이 10.49 km(`EngineDefines.h:59` UE_FLOAT_HUGE_DISTANCE) 안이다 [검증 상수, 적용은 추정].
- 머티리얼: 월드 위치 노이즈 노드 금지(655.36 m 거울 반복, WSDemote 83.9 km부터 1 cm — `HLSLMaterialTranslator.cpp:4937-4938,11994-11998`) [검증]. 지면 무늬는 청크 국소 UV + 생성기가 구운 정점 색으로 한다.
- 시드: 월드 시드는 uint64로 새로 둔다. 현재 `UTDSaveGame::MasterSeed`는 int32(`Source/TDGame/World/Persistence/TDWorldStateSubsystem.h:52-53`)이고 `FTDSeedContext`도 int32(`Source/TDWorldGen/Public/TDWorldGenTypes.h:14-15`) [검증·신규]. 허브는 기존 int32 그대로 둔다.
- 프로젝트 float 좌표: FluidFX 31개 파일(`01-engine-precision.md`)은 1,000 km에서 최소 단위 8 cm라 창 원점 기준인지 G0에서 코드로 확인한다(비평 3.10) [추정].

### 2.3 청크 크기와 상주 계층

청크 64 m를 고른 이유:
- 생성 비용이 청크 크기와 거의 무관하고 객체 수만 바뀐다(`01-proto-budget.md`, `proto/tables.md` 처리량 표) [검증].
- 64 m는 내비 타일 8 m로 나누어떨어진다(10 m는 아님) [검증 계산].
- Valheim 구역 64 m 선례(`01-web-infinite-tech.md`) [검증].
- numpy 13.5 ms/청크로 수학 병목 없음(`proto/timing.csv`) [검증].

계층별 반경(중심은 아래 표의 기준점, 해제는 적재 반경 + 16 m 이력):

| 계층 | 내용 | 기준점 | 적재/해제 반경 | 근거 |
|---|---|---|---|---|
| T0 데이터 | 작업 스레드 생성 결과(`FTDChunkData`) 캐시, 생물군 에셋 선로드 요청 | 폰 | 192 / 224 m | 화면 밖 관심 지점 표지·선로드 선행 시간 [추정] |
| T1 렌더·충돌 | 지형 메시, ISM, 충돌 쿠킹 완료, 게임플레이 액터 | 화면 중심(폰 + 카메라 전방 약 6.5 m) | 80 / 96 m | 화면 최원 꼭짓점 29.6 m(21:9에서 35.3 m) + 역광 그림자 최대 14 m + 15 m/s × 2 s 선행 = 약 80 m(비평 M1·M2) [검증 입력, 합산은 추정]. 최악 상주 약 12~17청크(`proto/tables.md`: 64 m 청크, 로딩 75 m→12, 103 m→17) |
| T2 시뮬 | 몬스터 활성·조우 스폰·동면 | 폰 | 활성 64 m, 동면 80 m | 스폰 고리 30~45 m(앞쪽 40 m+), 집에서 최대 추격 45 m(`Source/TDGame/MonsterAI/TDMonsterThinkSubsystem.h:64`) [검증]. T2 ⊂ T1 보장(충돌 해제 전에 동면) |
| T3 내비 | Recast 인보커 | 폰 | 생성 40 m / 제거 60 m | 내비 사용처는 클릭 이동·이동 준비 판정뿐(비평 M3) [검증] |

상주 메모리: 64 m 청크당 내비 제외 약 0.26 MB(렌더 포함 1.57 MB 중 내비 1.31 MB, `proto/tables.md`) [추정 모델]. T1 17청크면 지형·인스턴스·충돌 약 5~10 MB에 동적 메시 CPU 사본(청크당 0.8~1.2 MB, `01-engine-runtime-terrain.md` §6)이 더해진다. 무한 계통 전체 목표는 150 MB 이하다.

연속 이동 상한은 **15 m/s**다(64 m 청크에서 1.32~1.35청크/s, `proto/tables.md`) [검증 모델]. 더 빠른 이동은 G0 측정 뒤에 연다.

### 2.4 객체화 파이프라인·준비 판정

1. **T0, 작업 스레드**(`UE::Tasks`, 동시 2개 상한. 다른 세션이 같은 8코어를 씀): `FTDChunkGenerator::Generate`가 순수 데이터를 만든다. 목표는 C++ 청크당 5 ms 이하다(numpy 13.5 ms 기준 [검증], C++ 추정 1~3 ms).
2. **작업 스레드**: 메시 자료(`FDynamicMesh3` 또는 `FMeshDescription`)와 인스턴스 변환 배열을 만든다. 충돌은 비동기 쿠킹(`bUseAsyncCooking`, `DynamicMeshComponent.h:777` 기본 false → 켬) [검증].
3. **게임 스레드, 프레임 예산 1.5 ms**: 풀에서 `ATDTerrainChunkActor`를 꺼내 메시를 옮겨 붙이고(MoveTemp), ISM `AddInstances`를 일괄 호출하고(`InstancedStaticMeshComponent.h:275`) [검증], 게임플레이 액터는 풀에서 꺼낸다. 예산을 넘으면 다음 프레임으로 넘긴다.
4. **준비 판정**: 청크는 "충돌 쿠킹 완료 + 컴포넌트 등록 완료"일 때 준비 상태다. 기존 원칙 "미완료 상태로 이동하지 않는다"(`01-project-fit.md` 재사용 목록)를 따른다. 폰이 준비되지 않은 청크 경계 8 m 안에 들어서면 **D-45의 안전 감속(드물게, 발동 기록)**을 건다(`decisions.md:321-327` 통로 (a)) [검증]. 암전과 순간이동은 0회.
5. **해제**: 역순(T2 동면 → T1 반납 → T0 캐시 LRU 축출). 비동기 쿠킹 중 해제는 대기 중 쿠킹 중단 API(`BodySetup.h:345`) [검증]로 취소한다.

### 2.5 지형 그릇·충돌

- **1안(기본)**: 청크마다 `UDynamicMeshComponent` 1개. 1 m 격자(65×65 정점, 삼각형 8,192개), 정적 그리기 경로(`DynamicMeshSceneProxy.h:660`), 복합 충돌을 단순 충돌로, 재질 1개, LOD 하나. 근거는 `01-engine-runtime-terrain.md` §3.1·3.6 [검증].
- **2안(G0 비교)**: 런타임 `UStaticMesh` 빠른 빌드(`StaticMesh.cpp:8926-8929` 비에디터 빌드는 bFastBuild만) [검증] + `UStaticMeshComponent`. 동적 메시의 광선 추적 인스턴스는 매 프레임 CPU에서 수집되므로(`BaseDynamicMeshSceneProxy.cpp:676-690`) [검증], 정적 메시 프록시가 더 쌀 수 있다 [추정]. G0에서 게임 스레드 ms와 GPU 광선 추적 비용으로 판정한다.
- 광선 추적: 하드웨어 Lumen이 기본으로 켜져 있어(`LumenHardwareRayTracingCommon.cpp:16-22`, 비평 V4) [검증] 메시 지형도 간접광에 들어간다. 지형이 너무 비싸면 `SetEnableRaytracing`(`E:Source/Runtime/GeometryFramework/Public/Components/BaseDynamicMeshComponent.h:587,594`) [검증·신규]으로 끄는 대안을 G0에서 잰다(화면 공간 추적만 남음).
- Nanite·거리장 없음: 런타임 빌드가 불가능하고(`StaticMesh.cpp:8926-8929`, `DynamicMeshComponent.h:692-700`) [검증], 프로젝트는 Nanite가 꺼져 있어(`Config/DefaultEngine.ini:70`) 손실이 없다.
- 충돌 1단계는 삼각 메시 비동기 쿠킹이다(`ChaosCooking.cpp:212`, 에디터 가드 없음) [검증]. C 단계에서 편집 빈도가 측정 기준을 넘으면 2단계로 사용자 정의 Chaos 높이장 컴포넌트(`Chaos/HeightField.h:36-52` 공개 생성자·`EditHeights`) [검증]를 쓴다. 이 컴포넌트 경로는 미검증이라 C 관문의 실험 항목이다.
- 강·물: Water 플러그인은 쓰지 않는다(실험 단계, 렌더 재생성이 에디터 전용 — `WaterBodyComponent.cpp:1642-2132`) [검증·영향 추정]. 생성기가 강바닥을 높이에 파고 리본 동적 메시에 단일 물 재질을 입힌다.

### 2.6 생성기 C++ 이식

- 이식 원본: 프로토 `chunkgen.py`의 구조(정수 위치, splitmix64, 8방향 그래디언트, 5차 페이드, fBm 8옥타브 + 대륙 2옥타브 + 왜곡, 512 m 지역 구조물)를 그대로 따른다(`01-proto-chunkgen.md` §2) [검증].
- 차이: float64 대신 **Q16.16 고정소수점 + int64 중간값**을 쓴다. 높이 출력은 int32 mm다. 이유:
  - IEEE 기본 연산의 비트 동일성은 같은 바이너리·같은 경로에서만 보장된다(gafferongames, `01-web-infinite-tech.md`) [검증].
  - `/fp:fast`의 FMA 융합은 같은 표본도 호출 위치(벡터 본체 대 나머지 루프)에 따라 다르게 만들 수 있다(비평 V1 파급 ③) [추정].
  - 정수는 컴파일러·플래그·CPU와 무관하다.
- numpy 프로토와 비트 동등은 목표가 아니다. 프로토는 통계 기준(102 km 생물군 비율 차 0.7 %p 이하, 높이 표준편차 33 m대, `results.json`)으로만 쓴다. C++가 정본이다(D-40과 다른 새 결정, 7절).
- 순수 함수 계약: `Generate(seed, coord, version, neighborFrozenVersions, hubSeamProfile)` 외 입력 없음. 전역 난수 금지(D29 정규식 `Docs/MonsterAI_CombatSim/00-decision-record.md:95`) [검증]. `FMath::PerlinNoise2D`는 금지한다(float 절삭 + 256셀 주기, `E:Source/Runtime/Core/Private/Math/UnrealMath.cpp:3633-3636`) [검증].
- 시험(헤드리스 ①·게임 빌드 ②):
  - 이음매 비트 일치, 순서 무관, 청크 ±1e7·2^40(프로토 시험 28종 재현)
  - Editor와 Development Game 빌드의 1,000청크 해시 동일(`td.ChunkGen.DumpHashes` 콘솔 명령, 비출시 빌드 전용)

### 2.7 청크를 넘는 비국소 요소의 계층 계획

원칙은 Minecraft 구조물 집합과 같다. 각 계층은 자기 격자 칸마다 해시로 한 번 결정하고, 하위 계층은 유한 이웃만 조회한다(`01-web-infinite-tech.md` Structure_set) [검증]. 프로토가 512 m 구조물로 4청크 독립 생성 비트 일치를 확인했다(`results.json structures`) [검증].

| 계층 | 칸 | 결정 | 하위가 조회하는 이웃 |
|---|---|---|---|
| L0 대륙·기후 | 연속장 | 8192 m 옥타브, 온도·습도 → 생물군 | 점 평가 |
| L1 초지역 | 4096 m | 칸당 지터 노드 1~3개. **강**: 대륙 높이에서 가장 낮은 이웃 노드로 하류 연결(국소 규칙이라 누적 유량 대신 노드 고도 순위로 강 차수 근사). **도로**: 노드 사이 대칭 규칙(두 노드가 서로 최근접 2개 안에 있으면 연결). 교차점은 다리 세트피스 | 5×5 초지역(선분 길이 ≤ 2칸) |
| L2 지역 | 512 m | 관심 지점·세트피스 앵커 1회 시도(존재 확률, 칸 안 지터), 앵커 높이 = 그 점 1회 평가값 | 3×3 지역 + 반경 120 m |
| L3 청크 | 64 m | 높이(L0 + 강바닥·도로 깎기·세트피스 도장 혼합), 산포, 보행 격자 | 자기 + 경계 1표본 |

- 비용: 청크 하나가 초지역 25칸의 선분과 지역 9칸을 계산한다. 결과는 LRU 캐시(순수 데이터)에 둔다 [추정, G0에서 측정].
- 한계: 진짜 유역 누적(강 폭이 상류 전체에 비례)은 비국소라 근사한다. 강이 끊기지 않는지는 생성기 시험에서 "하류 연결 그래프에 순환 없음 + 바다 또는 호수 도달"로 검사한다.

### 2.8 산포: 자체 C++ (PCG 미사용)

PCG 런타임 생성(거대 볼륨 + 주변 셀)은 가능하다(`01-engine-runtime-pcg-nav.md` §1.2) [검증]. 그래도 무한 영역에서는 쓰지 않는다.

| 이유 | 근거 |
|---|---|
| 샌드박스 B는 생성물의 안정 ID(청크·층·순번)가 필요하다. PCG 출력은 Transient 파티션 액터라 재생성 때 정체성이 보장되지 않는다 | `PCGRuntimeGenScheduler.cpp:2341-2370` [검증] |
| Spawn Actor 노드는 동기 로드라 D-47과 충돌한다 | `PCGSpawnActor.cpp:122,138` [검증] |
| 지속 레벨에 에디터에서 저장한 `APCGWorldActor`가 필요하고, 위치 시드가 int32라 ±21,474 km에서 깨진다 | `PCGSubsystem.cpp:254-264`, `PCGHelpers.cpp:50-53` [검증] |
| 같은 산포 데이터가 몬스터 플로우 필드의 장애물 입력과 미니맵 색이 되어야 한다 | 3절·5절 설계 |
| 콜리전 ISM 등록과 내비 빌드 순서 문제(이중 빌드)를 생성기 한 번의 배치로 없앤다 | `01-engine-runtime-pcg-nav.md` §2.5 [추정] |

- 방식: 층별(큰 나무·바위 / 작은 풀·돌 / 상호작용 물체) 지터 격자 블루 노이즈. 칸 해시로 위치를 정하고, 간격 판정은 이웃 칸만 본다. 순번은 (층, 칸 행 우선 순서)로 고정한다.
- 그릇: 전부 **ISM**(HISM 안 씀). HISM은 변경마다 트리를 재빌드한다(`HierarchicalInstancedStaticMesh.cpp:2780-2830`) [검증]. 64 m 청크당 큰 41개·작은 410개 수준(`proto/tables.md`)이라 컬링 이득도 작다 [추정].
- ISM 단위는 G0에서 비교한다. (a) 청크 × 메시 종류(등록 컴포넌트가 많음) vs (b) 512 m 지역 × 메시 종류(지역 원점 기준, 청크 단위 일괄 추가·제거). 둘 다 2.2절 정밀도 규칙을 만족한다.
- 작은 물체는 `bVisibleInRayTracing=false`(`PrimitiveComponent.h:473`) [검증·신규]로 광선 추적 장면에서 뺀다. 인스턴스 10만 개 경고(비평 V4)에 대비한다.
- 허브는 손대지 않는다. 기존 PCG·랜드스케이프 그래프를 그대로 쓴다.

### 2.9 허브와 결합(걸어서 잇는 이음매, D-45)

- 허브 발자국 = 허브 랜드스케이프 사각형들의 합집합(필드 ±504 m, 별밭·고원). 오프라인 도구가 **랜드스케이프 가장자리 정점의 uint16 높이 원값**을 1 m 간격으로 뽑아 `FTDHubSeamProfile` 이진 자료로 굽는다(해시를 생성기 버전에 묶음). 랜드스케이프 충돌도 uint16 높이에서 만든다(`LandscapeCollision.cpp:1049-1121`) [검증]. 같은 정수에서 같은 변환식으로 Z를 계산하면 경계 정점이 맞는다 [추정, G1 측정].
- 높이 혼합: 발자국 밖 거리 d(정수 cm)에 대해 `H = lerp(H_경계연장, H_노이즈, smoothstep(d / 96 m))`. d=0에서 랜드스케이프 가장자리와 같고, 96 m 밖은 순수 생성이다.
- 정점 정렬: 랜드스케이프가 원점 중심 1 m 쿼드(D-05 결정 줄 `decisions.md:42`의 1008 m·1 m 쿼드)라면 경계는 정수 m 선이다. 1 m 청크 격자와 겹치므로 청크 메시는 발자국 안 쿼드만 빼면 된다 [추정: 랜드스케이프 정점의 월드 정수 정렬은 G0에서 확인].
- 틈 대비: 청크 쪽 이음매 변에 1 m 아래로 수직 치마를 둔다. 랜드스케이프 LOD가 바뀌어 생길 수 있는 미세 틈을 가린다. 탑다운 거리(9~35 m)라 LOD0이 대부분이다 [추정].
- 허브 열기: 허브 테두리의 막힘 요소(절벽·경계 차단물)를 걷어내는 콘텐츠 변경이다. 별밭(남)·고원(동)이 붙은 면을 피해 **북쪽 한 면부터** 연다(배치 `decisions.md:325`) [검증 배치, 선택은 추정]. G0·G1 초기는 본 허브가 아니라 **시험 맵**(작은 손 랜드스케이프 256 m)에서 한다. 되돌릴 수 있다.
- 대기: 허브 이계는 지금처럼 상자 포함 + 64단계 양자화 혼합(`Source/TDGame/World/Streaming/TDRealmSubsystem.cpp:34,90-97,831-860`) [검증·신규]. 무한 영역은 생성기 저주파 생물군 가중치를 같은 양자화 기계에 넣는다. 모든 생물군 태양은 D-46 규칙(빛 진행 yaw 225°±30°, 고도 55~70°, `decisions.md:329-334`) [검증]을 `UTDBiomeDefinition` 검증 함수로 강제한다.
- 데이터 레이어: 런타임 청크에는 없다(`Actor.cpp:7168-7197`) [검증]. D-45의 "게임플레이 활성화"는 `UTDChunkStreamingSubsystem::GetRegionIdAt(위치)` C++ 판정으로 대체한다.
- 허브 월드 파티션은 그대로 둔다(로딩 768 m 추정, `01-proto-budget.md`). 플레이어가 멀어지면 허브 셀은 스트리밍 소스 거리로 자연히 내려간다.

### 2.10 던전 아틀라스 겹침 해소

- 현재 아틀라스 원점은 (3000 m, 3000 m, 0), 슬롯 간격 300 m, 4열, 로딩 128 m다(`Source/TDWorldGen/Public/Dungeon/TDDungeonDefinitions.h:126,129,132,135`) [검증·신규]. 무한 지형이 그 XY를 덮으면 지표와 던전이 같은 높이에서 겹친다.
- 해소: **Z를 −8 km로 내린다.** 원점에서 최원 슬롯까지 약 9.7 km라 UE_FLOAT_HUGE_DISTANCE 10.49 km 안이고, 기본 KillZ `-UE_OLD_HALF_WORLD_MAX1`(−1,048,575 cm ≈ −10.48 km, `E:Source/Runtime/Engine/Private/WorldSettings.cpp:116`)보다 위다 [검증·신규]. 프로젝트 Config에 KillZ 재정의는 0건 [검증·신규]이고, 맵 WorldSettings의 저장값은 미확인이다 [추정].
- 위를 지나갈 때 던전 셀이 불필요하게 올라오지 않도록 스트리밍 소스를 격자별로 나눈다.
  - 플레이어 컨트롤러 기본 소스를 끈다.
  - 폰에 `UWorldPartitionStreamingSourceComponent`를 붙이고 `TargetBehavior=Exclude {던전 격자}`로 둔다.
  - 승강기(D-44)는 `Include {던전 격자}` 소스를 켠다.
  - 필드 존재: `E:Source/Runtime/Engine/Public/WorldPartition/WorldPartitionStreamingSource.h:157-174,427-431`, `E:Source/Runtime/Engine/Classes/Components/WorldPartitionStreamingSourceComponent.h:55-61` [검증·신규]. 동작은 [추정]이고 G1 회귀 시험으로 확인한다.

## 3. 내비·몬스터 AI·조우·결정론 시뮬

### 3.1 내비(Recast, 플레이어 전용)
- `bGenerateNavigationOnlyAroundNavigationInvokers=True`(`NavigationSystem.h:391`) [검증]. 플레이어 폰 인보커는 생성 4000 / 제거 6000 cm다(비평 M3 권장) [검증 근거].
- `bFixedTilePoolSize=True`, `TilePoolSize=1024`(필요 약 π·(60/8+0.71)² ≈ 212타일 × 층 1~2, 여유 2배 이상) [추정 계산]. 크기 조절 풀은 거대 경계에서 Error 로그를 남기고 자른다(`RecastNavMeshGenerator.cpp:5748-5773`) [검증].
- `NavMeshBoundsVolume` ±1e8 cm 1개(전 세계 플래그는 엔진이 막아 둠, `NavigationSystem.h:365-371`) [검증].
- `TileSizeUU` 800(청크 64 m에 8타일 정렬). G0에서 800·1000·1600을 비교한다(비평 E3).
- `bDoFullyAsyncNavDataGathering=false`를 유지한다(L-editor-09, `Docs/Lessons/editor.md:75-81`) [검증].
- 시각 장식 ISM은 `bCanEverAffectNavigation=false`. 큰 바위·나무만 내비에 기여한다.
- **파급(허브 포함 전역 설정)**: 허브 내비도 플레이어 주변만 생긴다. 목적지 내비 투영으로 준비를 판정하던 `TDSeamlessTravelSubsystem.cpp:422-426` [검증]은 "청크·셀 충돌 준비"로 바꿔야 한다. 클릭 이동 목적지는 화면 안(≤35 m)이라 인보커 40 m로 덮인다.

### 3.2 몬스터 길찾기(M3-04 재정의)
- 현재는 "방 단위 플로우 필드, todo"다(`Docs/MonsterAI_CombatSim/07-roadmap-and-tasks.md:503-511`) [검증]. 몬스터는 내비 없이 직선 접근 + 회피만 한다(비평 M3) [검증]. 무한 지형에는 방이 없다.
- 재정의(**M3-04w 창 플로우 필드**):
  - 목표(플레이어) 중심 128 m 창, 1 m 칸(16,384칸), 2 Hz, 4프레임 결정적 분할 재계산. 원래 M3-04의 주기·분할 조건을 유지한다.
  - 입력은 `FTDChunkData::WalkabilityGrid`(경사·물·큰 산포 발자국)에 B의 설치물을 겹친 것이다. 둘 다 정수 자료라 해시 결정론이 쉽다.
  - 창 밖 몬스터는 창 가장자리를 향해 직진한다.
- Recast와 분리하는 이유:
  - 내비 타일 수가 몬스터 수·활성 반경과 무관해진다.
  - 결정론 시뮬레이터가 같은 격자를 만들 수 있다(엔진 내비 없이). 시뮬에서 생성기(seed, coord)로 실제 지형 아레나를 뽑아 장애물 있는 시나리오를 만든다. 지금 아레나는 반경 1500 평지다(`04-combat-simulator.md:424`, 비평 3.4) [검증].
- B를 열 때 필수 원시 행동은 "막힘 → 구조물 공격"이다(`01-web-design-fit.md` §3.3 착취 문제) [검증 사례].

### 3.3 조우·거리별 난이도
- 조우 칸 128 m(2×2 청크)마다 슬롯 N개를 둔다. 시드 = D29 규약 확장 `HashCombine(월드시드, "Encounter", 칸X, 칸Y, 슬롯)`(`00-decision-record.md:54` 규약) [검증 규약].
- 스폰 위치: 화면 밖이면서 T2 활성 반경 안이다(30~45 m, 진행 방향 앞쪽 40 m+). 카메라 요 45° 고정이라 화면이 전방으로 치우친다(`01-engine-runtime-pcg-nav.md` §3) [추정].
- 난이도 = f(허브 중심 거리)를 500 m 단위 단계로 하고 상한에서 평평하게 만든다. 생물군·도로 근접으로 보정한다. 처치 기록은 (조우 칸, 슬롯, 처치 게임 시각)으로 청크 레코드에 둔다. 런타임 스폰은 에디터 GUID가 없다(`TDPersistentStateComponent.cpp:34-43`) [검증].
- 청크 해제와 몬스터:
  - 전투 중이 아닌 몬스터는 T2 동면 반경(80 m)에서 상태를 슬롯 기록에 접고 두뇌 슬롯을 반납한다(`TDMonsterBrainSlot.h:12-14`) [검증].
  - 집 청크가 해제되면 귀환 대신 화면 밖에서 소멸시킨다.
  - 동시 활성 수는 반경에 묶여 상수다. 기존 틱 예산(300마리 4.0 ms, `03-tick-and-scale.md:16,20`) [검증]과 충돌하지 않는다.
- 몬스터 정의 JSON과 클래스는 생물군 선로드 묶음에 넣는다(D-47).

### 3.4 부동소수점과 시뮬
- 생성기는 정수라 Game/Editor 차이에서 빠진다. 전투 시뮬 골든 해시의 Game/Editor 차이(비평 V1)는 이 설계 범위 밖의 별도 위험이다. 다만 G0의 "게임 빌드 해시 덤프" 계층(비평 3.7 ②)을 만들면 전투 시뮬에도 재사용할 수 있다.

## 4. 저장

### 4.1 파일 구조
```
SaveGames/<슬롯>/world.meta          형식 버전, 월드 시드 uint64, 현재 생성기 버전, 허브 레코드(기존 ActorRecords·DungeonStates 이관)
SaveGames/<슬롯>/r.<rx>.<ry>.tdr      영역 파일 = 32×32 청크(2,048 m). 머리 1024칸(오프셋·길이·CRC32) + 방문 비트(청크당 64비트 = 8 m 소구역)
                                      + 압축 청크 레코드
```
- 영역 분할 근거: Minecraft .mca 32×32·섹터 선례(`01-web-infinite-tech.md`) [검증]. 손대지 않은 청크는 레코드가 없다. 생성기 재생성 + 방문 비트만 있다.

### 4.2 청크 레코드
| 필드 | 형식 | 수준 |
|---|---|---|
| 청크 좌표 | int64 ×2 | 공통 |
| 동결 생성기 버전 | uint16(첫 변경 시 기록) | B·C |
| 생성물 제거 비트셋 | 층별 비트셋(순번 색인) | B |
| 설치물 | {설치 ID uint32(영역 안 단조 증가), 종류 uint16, 청크 국소 위치 int16×3(cm, 1 cm 양자화), 요 uint16, 상태 uint16} | B |
| 높이 차분 | 첫 편집 시 청크 높이 격자 65×65 int16(mm 차분) 통째 승격, 약 8.3 KB | C |
| 조우 상태 | {슬롯, 처치 시각} | 공통 |

- **생성물 안정 ID** = (청크 X, 청크 Y, 생성기 버전, 층 uint8, 순번 uint16). 같은 버전의 같은 청크는 정수 생성기라 순번이 같다(2.6절).
- **생성기 버전 동결**:
  - 처음 바뀐 청크는 그 시점 버전으로 영구히 재생성한다. 런타임은 옛 버전 생성기(`FTDTerrainFieldV1`…)를 계속 들고 있다.
  - 이웃 버전이 다른 경계는 새 버전 청크가 옛 이웃의 경계 높이를 받아 16 m에 걸쳐 섞는다. 이웃 동결표가 생성 입력이라 순수 함수가 유지된다.
  - 출시 뒤 생성기 변경은 "추가 층"을 기본으로 하고, 지형 모양 변경은 버전을 올린다(No Man's Sky 재생성 문제, `01-web-infinite-tech.md`) [검증 사례].
- **차분 상한**:
  - 청크 설치물 2,048개, 압축 레코드 64 KB, 월드 T1 상주 설치 인스턴스 5만 개. G0의 E4-lite로 확정한다.
  - 건축가 모델 청크당 1.53만 개(`01-proto-budget.md`)와 광선 추적 10만 개 경고(비평 V4)를 함께 본 출발값이다 [추정].
  - 상한에 닿으면 설치를 거부하고 안내한다(NMS식 편집 중지 선례).
- 크기: 100시간 0.9~16 MB(`proto/tables.md` 100시간 세이브) [추정 모델]. GQ-22 목표(본편 6~8시간 + 반복 10시간 이상)에서는 훨씬 작다.

### 4.3 원자적 쓰기·백업
- [검증·신규] 엔진 `IFileManager::Move(…, Replace=true)`는 원자적이지 않다. 대상을 먼저 지우고 `MoveFileW`를 부른다(`E:Source/Runtime/Core/Private/HAL/FileManagerGeneric.cpp:299-323`, `E:Source/Runtime/Core/Private/Windows/WindowsPlatformFile.cpp:1216-1218`, REPLACE_EXISTING 플래그 없음). 기본 세이브는 최종 파일을 직접 덮어쓴다(`FileHelper.cpp:738-751`, 비평 V7) [검증].
- 절차:
  1. `.tmp`에 쓰고 닫기·플러시
  2. 기존 `.bak` 삭제
  3. 현재 파일 → `.bak`
  4. `.tmp` → 최종
- 읽기 우선순위: 최종(CRC 통과) → `.tmp`(CRC 통과) → `.bak`. 어느 단계에서 끊겨도 완전한 세대 하나가 남는다.
- 비동기: 게임 스레드는 더러운 청크 레코드 사본만 만든다(≤2 ms). 직렬화·압축·쓰기는 작업 스레드에서 영역 파일 단위로 한다. 자동 저장 주기는 60초 + 영역 이탈 시다.
- 기존 `UTDSaveGame` 형식 버전 1(`TDWorldStateSubsystem.h:47-50`) [검증·신규]은 마이그레이션 표 골격(`TDWorldStateSubsystem.cpp:84-127`, 비평 3.2) [검증]으로 `world.meta`에 이관한다.

## 6. 콘텐츠·에셋 양과 단조로움 대책

- 현황: 다크 판타지 자연 메시는 약 30개다(Birch 4, Bush 1, Grass 1, Rocks2 3, Nature 18, TerrainModules 1, 비평 3.5) [검증]. 생물군 하나도 빠듯하다.
- 생물군 1개 최소 묶음 [추정, 비평 3.5]: 지면 재질 4~6, 큰 물체 10~20, 작은 물체 20+, 관심 지점 템플릿 40+. A 단계는 **생물군 2개**(잿빛 골짜기 묶음 확장 + 새 1개)로 시작하고 무한은 L0 기후장이 둘 사이를 교대·변주하게 한다.
- 변주 축은 ISM 인스턴스별 크기·색조·회전·풍화(사용자 자료 float), 세트피스 × 생물군 재질 교체, 산포 규칙 조합이다. 반복 체감은 시간당 관심 지점 180~360개 소비(`01-web-design-fit.md` §3.1) [추정]가 기준이다.
- **단조로움은 오프라인으로 잴 수 있다**(기술 우선의 이점): 생성기가 순수 함수라 단조로움 감사 커맨드렛이 무작위 보행 경로 1,000개 × 10시간을 몇 분 안에 생성 데이터만으로 걷는다. 그리고 "같은 세트피스 템플릿 재노출 간격 중앙값", "관심 지점 간격 60~120 m 준수율"을 출력한다. 관문 G2의 합격 기준이 된다.
- 손 설계 세트피스 배치:
  - (가) L2 512 m 지역 칸 1회 시도(밀도 균일, Hytale 점 격자식)
  - (나) 거리 고리 랜드마크(Minecraft 요새식, 허브 거리 2·5·10 km 고리마다 보장) — 장거리 목표
  - (다) 도로 교차·강 교차 전용 세트피스(다리·여관)
  - 근거는 `01-web-design-fit.md` §3.5 [검증 사례]. 세트피스는 에디터 레벨에서 저작하고 굽기 도구가 `UTDSetPieceDefinition`(높이 도장, ISM 목록, 스폰점)으로 변환한다. 런타임 레벨 적재가 없으므로 월드 애셋 스트리밍(실험, 등록 수 선형 비용, `WorldPartitionRuntimeHashSet.cpp:719-724,1439-1460`) [검증]의 위험을 지지 않는다. 반복 템플릿 사이 GUID 겹침(`ActorInstanceGuids.cpp:132-160`) [검증]도 생기지 않는다.
- 비용: 세트피스 첫 12~20개, 생물군 2개의 메시 보강은 아트 작업이 지배한다. 기술 로드맵과 병렬로 둔다(8절 P2).

G0 합격 기준(전부 충족):
- E1: 게임 스레드 청크당 객체화 p95 ≤ 2.0 ms(시간 분할 합계). 15 m/s 직선 2 km에서 프레임 p99 < 33.3 ms. 9 m/s 이하에서 안전 감속 발동 0회. 작업 스레드 생성 ≤ 5 ms/청크.
- E2: Editor와 Development Game의 1,000청크 해시 동일. 이음매 비트 일치 28/28. 순서 무관.
- E3: "Navmesh bounds are too large" 0건, "tile limit reached" 0건(풀 1024). 15 m/s에서 클릭 목적지(≤30 m) 투영 성공 ≤ 0.5 s. 타일당 메모리 실측.
- E4-lite: T1 링 + ISM 1만 개, 하드웨어 Lumen 켬 상태에서 GPU 프레임 중앙값 ≤ 16.7 ms. 미달이면 지형 광선 추적 끔으로 재측정해 통과 여부와 화질 차이를 기록한다.
- 시험 맵 랜드스케이프 경계 이음매 높이 차 ≤ 1 cm(정점 표본 전수).
- 실패 시 분기: E1 미달 → 2안(런타임 정적 메시)·32 m 하위 메시 분할·ISM 지역 단위로 재시도(+3일). E4 미달 → 광선 추적 제외 정책 확대. E2 미달은 정수 설계상 버그이므로 수정한다.
- **되돌릴 지점**: 새 모듈·시험 맵·콘솔 명령만 있음. 삭제하면 원상복구된다. 허브·Config 무변경(내비 설정은 시험 맵 전용 오버라이드로 측정).

### P1 — 수준 A 본체 (6~8주)
- 생성기 V1 완성(L1 강·도로, L2 세트피스 앵커), 생물군 대기 혼합, 조우·거리 난이도, 미니맵·방문 안개, 저장 v2(영역 파일·방문·처치), 본 허브 북쪽 한 면 열기(콘텐츠), 내비 전역 설정 전환 + 이동 준비 판정 교체, 던전 아틀라스 이전.
- **G1 기준**:
  - 허브에서 실제 이동 입력으로 30분 연속 보행(자동 입력 구동), 순간이동·암전 0, 낙하 관통 0
  - 허브 경계 높이 차 ≤ 1 cm, 프레임 p99 < 33.3 ms
  - 30분 메모리 증가 < 50 MB
  - 저장·불러오기 왕복으로 방문·처치 복원, 3단계 쓰기 강제 종료 100회 손상 0(E5)
  - 던전 승강기 회귀 통과
- 되돌릴 지점: 허브 테두리를 다시 막고 내비 설정을 되돌리면 기존 유한 세계로 돌아간다(무한 코드는 플래그로 꺼짐).

### P2 — 콘텐츠 (P1과 병렬, 아트 주도)
- 생물군 2 → 4, 세트피스 12~20개, 굽기 도구, 단조로움 감사 커맨드렛.
- **G2 기준**: 무작위 경로 1,000개 × 10시간에서 같은 세트피스 재노출 간격 중앙값 ≥ 15분, 관심 지점 간격 60~120 m 준수율 ≥ 80 %, 거리 고리 랜드마크 도달 경로 100 %.

### P3 — 수준 B (6~8주)
- 격자 배치(0.5 m 맞춤, 내비 타일 정렬), 생성물 철거, 청크 레코드, 컷아웃 확장, M3-04w 창 플로우 필드(E7), "막힘 → 구조물 공격" 원시 행동, 시뮬 장애물 입력.
- **G3 기준**:
  - 설치·철거 1회 게임 스레드 ≤ 1 ms, 내비 갱신 ≤ 1 s
  - 청크 1개에 설치물 2,048개 + T1 링 5만 인스턴스에서 60 fps(RTX 2060 1080p)
  - 저장 게임 스레드 ≤ 2 ms
  - 플로우 필드 300마리 비용이 유닛 수와 무관하고 해시가 순서와 무관
  - 벽 뒤 몬스터가 우회 또는 공격으로 도달 100 %
- 되돌릴 지점: 설치 기능 플래그 끔(레코드는 무시하고 읽기만).

### P4 — 수준 C, 2.5차원 높이 편집 (4~6주)
- 높이 차분 격자, `FastNotifyPositionsUpdated`, 충돌 재쿠킹 묶음(0.25 s 디바운스) 또는 사용자 정의 Chaos 높이장, 내비 Geometry 더럽힘 디바운스 0.5 s.
- **G4 기준**: 편집 1회 프레임 < 33.3 ms, 내비 반영 ≤ 1 s, 분당 100회 편집 지속 60 fps, VSM 무효화 페이지 수 기록(E9).
- 되돌릴 지점: 높이 차분 무시 플래그.

합계 [추정]: A 3~4개월(P0+P1, P2 병렬), B +1.5~2개월, C +1~1.5개월. 1단 project-fit 추정(A 3~5개월, B +1~2, C +3 이상)보다 C가 짧다. C를 2.5차원으로 한정하고 A의 지형 그릇을 처음부터 높이 편집 가능하게 골랐기 때문이다.

1단 실험 목록과의 차이: E6(PCG 비교)은 PCG를 쓰지 않으므로 뺀다. E8(월드 애셋 스트리밍)은 데이터 프리팹으로 대체하므로 뺀다. E10(정밀도 순간이동)은 P1 끝에 0.5일로 확인한다.

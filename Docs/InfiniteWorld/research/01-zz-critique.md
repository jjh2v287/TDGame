## 0. 결론 요약

1. 1단 9갈래의 큰 결론(수준 A·B 가능, 수준 C는 별도 그릇, 랜드스케이프·월드 파티션 셀 생성은 런타임 불가, 좌표 정밀도는 걸림돌 아님)은 서로 모순 없이 유지된다.
2. 수치 모순 10건 중 결론을 바꾸는 것은 2건이다. 둘 다 반경 값을 줄이는 쪽이다.
   - 상주 반경: proto-budget의 78 m는 태양 고도 25도를 가정했다. 실제 결정 D-46은 태양 고도 55~70도이고 빛이 카메라 반대 방향(역광)이다. 이를 적용하면 렌더 상주 반경은 약 44~50 m다.
   - 내비 인보커: 몬스터는 내비메시를 쓰지 않는다. 따라서 인보커 반경은 몬스터 활성 반경이 아니라 클릭 이동 범위(화면)로 정한다.
3. 이번 직접 검증에서 새로 드러난 높은 위험 3건:
   - (가) 부동소수점 모드: Game 타깃은 `/fp:fast`, Editor 타깃과 헤드리스 시험은 `/fp:precise`로 컴파일된다 [검증]. 무한 생성 결정론과 기존 전투 시뮬레이터의 골든 해시에 함께 영향을 준다.
   - (나) Lumen 하드웨어 광선 추적: 이 프로젝트에서는 기본으로 켜진다. 엔진 스스로 "인스턴스 10만 개 이상에서 장면 갱신 비용이 크다"고 경고하는데, 샌드박스 B 건축가 시나리오(기지 약 24.5만 개)가 이 선을 넘는다 [검증].
   - (다) 세이브 쓰기가 최종 파일을 직접 덮어쓴다. 임시 파일 뒤 교체 방식이 아니다 [검증]. 무한 세계는 세이브가 커지고 쓰기가 잦으므로 손상 위험이 커진다.
4. 가장 큰 공백 두 가지:
   - GPU 측 비용(RTX 2060의 광선 추적용 메시 가속 구조 빌드, 가상 섀도 맵, VRAM)을 아무 갈래도 모델링하지 않았다.
   - 콘텐츠 양: 현재 자연 환경 메시는 약 30개다 [검증]. 무한 세계의 실제 병목은 엔진이 아니라 에셋 양일 가능성이 높다.

## 3. 빠진 관점

### 3.1 멀티플레이·네트워크
- 현재 코드는 싱글이다. 복제가 꺼져 있고 RPC가 0건이다 [검증, M9]. 다만 GQ-22는 결정 대기 상태다.
- 1단의 비용 추정(생성 소스 1개, 내비 인보커 1개, 단일 세이브 권한)은 모두 싱글을 전제로 한다. 멀티를 하면 다음이 추가로 필요하다. 서버에서 플레이어 수만큼의 스트리밍 중심, 흩어진 플레이어마다의 내비와 PCG, 청크 권한 경합, 생성기 결정론의 기계 간 일치(정수 생성 필수). 이 비용은 평가되지 않았다.
- 권장: **무한 세계를 시작하기 전에 GQ-22를 싱글로 확정한다.** 그러면 1단의 추정이 그대로 유효하다.

### 3.2 세이브 손상·버전 이동
- 현재 구조: 직접 덮어쓰기 [검증 V7], 단일 슬롯, 동기 저장, 세계 전체를 메모리 TMap에 보관(project-fit). 마이그레이션 표 골격은 있다(`TDWorldStateSubsystem.cpp:84-127` [검증]).
- 무한 세계 고유 위험:
  - (가) 쓰는 도중 종료되면 세계 전체를 잃는다.
  - (나) 생성기가 바뀌면 "생성물 k번 제거" 같은 차분이 다른 물체를 가리킨다. 의미상의 손상이다.
  - (다) V1의 부동소수점 차이: 패치로 컴파일러나 최적화가 바뀌면 생성물 순번이 밀릴 수 있다.
  - (라) 세이브가 커질수록 전체를 다시 쓰는 비용이 커진다.
- 대책:
  - 영역 파일 분할(예: 32×32 청크, Minecraft .mca 선례는 web-infinite-tech 참조)
  - 임시 파일에 쓴 뒤 교체(`IFileManager::Move`)
  - 2세대 백업
  - 청크 레코드 검사합(CRC, 순환 중복 검사)
  - 청크별 생성기 버전 기록과, 변경된 청크의 생성물 동결
  - 생성물 정체성은 정수로만 정함(V1)

### 3.3 목표 사양 RTX 2060 1080p 성능·메모리
- 1단의 메모리 모델(proto-budget 35 MB)은 CPU 측만 다룬다. 다음 GPU 측 항목은 어느 갈래도 모델링하지 않았다.
  - 하드웨어 광선 추적이 켜져 있으므로 [검증 V4] 런타임 생성 동적 메시마다 하위 가속 구조(BLAS) 빌드가 GPU에서 일어난다.
  - 인스턴스가 늘수록 상위 가속 구조(TLAS) 갱신 비용이 커진다(10만 개 경고).
  - 가상 섀도 맵 페이지가 무효화된다(Nanite가 꺼져 있어 비 Nanite 패스로 다시 그림).
  - RTX 2060의 VRAM 6 GB(일반 사양 [추정]) 안에서 위 항목을 모두 감당해야 한다.
- 1080p 16:9가 기준이면 21:9 확장은 부차적이다.
- 판정: 무한 세계 가능성의 '성능' 근거는 현재 CPU 수학 측정뿐이다. 엔진 객체화와 GPU 비용이 핵심 미지수다(2단 E1·E4).

### 3.4 결정론 전투 시뮬·몬스터 AI와의 결합
- (가) 길찾기: 몬스터는 길찾기가 없다 [검증 M3]. 예정된 M3-04는 **'방 단위' 플로우 필드**(todo, `07-roadmap-and-tasks.md:503-511` [검증])인데, 무한 지형에는 방이 없다. 목표를 중심으로 한 창(예: 128 m) 플로우 필드로 다시 정의하고, 적재된 청크의 높이·장애물·설치물을 입력으로 받아야 한다. 샌드박스 B에서는 설치물이 몬스터의 경로를 막는다(web-design-fit의 착취 문제). 길찾기가 없으면 벽 하나로 몬스터가 완전히 무력화된다.
- (나) 시뮬 아레나: 반경 1500에 장애물이 없다(`04-combat-simulator.md:424` [검증]). 지형과 설치물의 영향은 밸런스 시뮬 밖에 있다.
- (다) 난수 규약: 월드 생성용 정수 해시 난수와 D29 이름 있는 난수 스트림을 한 규약으로 묶을지 정해야 한다.
- (라) 부동소수점: V1이 시뮬과 생성 양쪽에 같은 영향을 준다.
- (마) 몬스터 영속성: 무한 세계의 몬스터는 런타임 스폰이라 에디터 GUID가 없다(project-fit). 처치 기록은 (청크 좌표, 스폰 순번) 키로 남겨야 한다.
- (바) 청크 해제와 몬스터: 집에서 45 m까지 추격하는 몬스터가 해제되는 청크로 넘어갈 때의 규칙(동결, 귀환, 제거)이 필요하다.

### 3.9 사용자 선호(연속 보행·암전 거부)와의 정합
- D-45(순간이동 0회, 연속 세계) [검증 `decisions.md:321-327`]와 무한 청크 보행은 잘 맞는다.
- 충돌점:
  - (가) **GQ-08 '빠른 이동 없음'(권장값) + 무한 = 귀환 거리가 끝없이 늘어난다.** 이동식 거점이나 탈것이 필요하다. 탈것의 연속 이동 상한(proto-budget 15 m/s)이 생성률을 정한다.
  - (나) GQ-08이 예외로 둔 사망 부활 이동은, 먼 거점으로 부활할 때 대상 청크를 적재하는 동안 기다려야 한다. 이는 암전이나 대기 화면과 같다. D-44식 '움직이는 대기'로 연출하거나 부활 지점을 가까운 쉼터로 제한해야 한다.
  - (다) 허브(약 1.5 km² 월드 파티션)와 생성 영역의 경계는 D-45 방식(실제 지형 연결)이어야 한다. 경계 높이 이음매가 필요하다.
  - (라) D-45는 '데이터 레이어로 지역 구분과 게임플레이 활성화'를 한다. 그런데 런타임 청크에는 데이터 레이어가 없다(wp-runtime [검증 갈래]). 생성 영역의 활성화는 위치 기반 C++ 판정으로 해야 한다.

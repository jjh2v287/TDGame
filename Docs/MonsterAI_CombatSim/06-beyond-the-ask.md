# 06. 요구사항 밖의 추가 고려사항

작성 2026-09-10. 입력: 완전성 비평(`research/zz-completeness-critique.md`), 결정 기록(구속력), 심사 판정, 최종 문서 [01](01-ai-model-decision.md)·[02](02-architecture-and-definition-format.md)·[03](03-tick-and-scale.md)·[04](04-combat-simulator.md)·[05](05-ml-and-generative-ai.md)·[07](07-roadmap-and-tasks.md). 이 문서는 다른 문서가 이미 정한 것을 다시 쓰지 않고 링크한다. 할 일 ID 는 07 문서의 `M<phase>-<번호>` 체계와 충돌하지 않도록 기존 번호 다음부터 "(제안)" 을 붙여 적었고, 07 문서에 옮겨 적기 전까지는 효력이 없다.

## 이 문서가 답하는 질문

1. 사용자의 여섯 번째 질문 "이것 외에 내가 생각하지 못한 무언가는 또 뭐가 있는가" 에 우선순위를 붙여 답하면 무엇인가.
2. 비평이 찾은 누락 주제 20개와 요구사항 밖 고려사항 14개 가운데 무엇이 이미 최종 문서에 들어갔고 무엇이 비어 있는가.
3. 조사 16편 사이의 모순 13건은 최종적으로 어떻게 판정됐고, 결정 기록과 어긋나는 것이 있는가.
4. 사람과 에이전트가 함께 이 툴을 운영하려면 어떤 규칙(골든 해시 소유, 문서=코드, 저장, 텔레메트리, 시각화, 벤치, 업그레이드)이 더 필요한가.
5. 난이도·스폰·보스 스크립트·군중제어·무리 전술 같은 게임 설계 요소는 어느 JSON 에 어떤 모양으로 들어가는가.

## 결론 요약

- 최종 문서 6편은 조사의 "엔진 능력" 결론과 비평의 운영 규약 가운데 **결정론·판정 경로·생성형 AI 루프·골든 해시 절차·환경 지문**은 이미 흡수했다. 비어 있는 것은 **콘텐츠 모델(난이도·웨이브·넉백·무리)·텔레메트리·기획자용 시각화·벤치마크 하네스·세이브 직렬화** 다섯 묶음이다(§1·§2).
- 누락 주제 20개의 반영 상태는 이미 반영 2(M1 일치 검증, M4 대리 봇 입력 모델) / 부분 반영 15 / 미반영 3(M5 난이도, M13 시각화, M15 텔레메트리)이다(§2).
- 요구사항 밖 고려사항 B1~B14 의 반영 상태는 이미 반영 3(B2·B6·B10) / 부분 반영 9 / 미반영 1(B14 세이브) / 결정 기록 미채택 1(B1, 대안은 §1-1)이다(§2-2).
- 모순 13건의 판정은 모두 비평과 같고 결정 기록과도 충돌하지 않는다. 단 **C2(GE(Gameplay Effect, 게임플레이 효과) 만료 스텝)** 는 결정 기록 D27(1/64 스텝)을 따르되, "1초 지속 효과의 만료 스텝은 적용 시점 기준(틱 함수 안에서 스텝 k 에 적용)으로 두뇌 관측 스텝 = k+65, 타이머 발화 스텝 = k+64" 라는 기준을 04 문서 기대값에 명시해야 한다(§3, 추정 — `OneStepPerFrame` 골든으로 확정).
- 비평 B1 "UObject·월드 비의존 순수 커널" 은 결정 기록(D13~D18: 월드 서브시스템 + `World->Tick` + ASC(Ability System Component, 어빌리티 시스템 컴포넌트) 유지)이 채택하지 않았다. 이 문서는 결정 기록을 따르되, 같은 효과를 "커널 계층 규율(정적 단언·파일 목록·허용 include 목록)" 로 얻는 대안을 §1-1 에 적는다.
- 게임 설계 요소는 몬스터 정의 JSON 이 아니라 **시나리오 JSON(난이도·스폰 테이블·가상 카메라)** 과 **몬스터 정의 JSON(페이즈 스크립트·군중제어 반응·무리 역할)** 로 나뉘어 들어간다. 스키마 조각은 §5 에 있다.
- 사용자 결정이 필요한 것은 8건이다(§6). 착수 전에 답이 필요한 것은 KPI(Key Performance Indicator, 핵심 지표) 문서 소유자(§6-2)와 텔레메트리 수집 범위(§6-3)다.

## 5. 게임 설계 요소가 시뮬·AI 에 들어오는 콘텐츠 모델

원칙: **플레이 상황(난이도·스폰·카메라)은 시나리오 JSON, 몬스터 고유 반응(페이즈 스크립트·군중제어 반응·무리 역할)은 몬스터 정의 JSON.** 두 파일 모두 미지 키 거부(02 규칙 2)를 지키므로 아래 키는 스키마 확장(`schema` 정수 증가)으로 들어간다.

### 5-1. 난이도 스케일링 — 시나리오 JSON

```json
"difficulty": {
  "id": "Hard",
  "monster_stat_scale": { "max_health": 1.6, "attack_power": 1.3, "move_speed": 1.05 },
  "monster_action_pool": "hard",
  "ai_override": { "think_hz": 12, "inertia": { "switch_ratio": 1.1 } },
  "player_level": 12
}
```

`monster_stat_scale` 은 `UTDEquipmentStatEffect` 와 같은 Multiplicative GE 로 적용해 공식 경로를 바꾸지 않는다(04 §9.2). `monster_action_pool` 은 정의의 `actions[].pools` 태그(선택 키)와 대조해 풀에 없는 행동을 제거한다. 시뮬 매트릭스 축에 `difficulty.id` 가 들어가고 결과 행에 열이 추가된다.

### 5-2. 스폰·웨이브 테이블 — 시나리오 JSON

```json
"spawn_table": [
  { "at_step": 0,    "definition": "Goblin_Melee", "count": 6, "spawn": { "ring_radius": 900 }, "wave": "w1" },
  { "at_step": 640,  "definition": "Archer",       "count": 4, "spawn": { "at": [0, 1100] },   "wave": "w2" },
  { "at_step": 1280, "definition": "Ogre_Boss",    "count": 1, "spawn": { "at": [0, 1300] },   "wave": "boss",
    "when": { "wave_cleared": "w2" } }
]
```

규칙: 항목은 `at_step` 오름차순, 동률은 배열 순, `when` 이 있으면 `at_step` 과 조건 모두 만족한 첫 스텝. SimulationId 는 시뮬에서는 스폰 시각 순으로 단조 증가(D14·D30 확장)하고, 게임은 03 §2 의 슬롯 재사용 규칙(프리리스트 후입선출 + 세대 번호)을 그대로 따른다. 기존 `monsters` 배열은 `spawn_table` 의 `at_step: 0` 단축형으로 남긴다.

### 5-3. 보스 페이즈·스크립트 이벤트 — 몬스터 정의 JSON

```json
"phases": [
  { "id": "Enraged", "enter_when": { "input": "SelfHealthRatio", "op": "<=", "value": 0.5 },
    "on_enter": "Roar_Enrage",
    "on_enter_events": [
      { "do": "SetInvulnerable", "steps": 96 },
      { "do": "Spawn", "definition": "Goblin_Melee", "count": 4, "ring_radius": 400 },
      { "do": "ForceSequence", "sequence": "Smash_Combo", "once": true } ] } ]
```

이벤트는 결정 로그에 `ev:"phase_event"` 로 남고(D34), `Spawn` 은 Spawn 스트림·SimulationId 규약을 그대로 쓴다. 무적은 (추정) `TDDamageFormula::Compute` 앞의 게이트 또는 Multiplicative 0 GE(04 §9.2 방식)로 두어 판정 경로를 하나로 유지한다(D18). `FTDDamageRule` 은 {Event, Actions} 트리거 구조(`TDDamageTypes.h:255-266`)라 피해 차단 게이트로 쓸 근거가 없고, 확장 여부는 04 미결 3 과 함께 결정한다.

### 5-4. 넉백·군중제어 규약 — 몬스터 정의 JSON + 공용 순수 함수

```json
"cc_response": {
  "stagger_steps": 20,
  "knockback": { "mass_scale": 1.0, "decay_per_step": 0.85, "max_distance": 300 },
  "immune": ["Freeze"],
  "ai_during_cc": "blocked"
}
```

규약 3줄: (1) 군중제어 중 두뇌 입력은 차단(`ai_during_cc`), 사고는 해제 스텝에 강제 1회(07 M1-04 와 동일). (2) 이동은 `FTDKnockback::Integrate(Pos, Vel, Decay, Step)` 순수 함수가 적분기를 덮어쓰고, 공간 해시 갱신·자리 토큰 반납은 평소 규칙대로 스텝 끝에. (3) 타이머·GE 만료는 멈추지 않는다(M19 의 엔진 순서와 정합). 게임과 시뮬이 같은 함수를 쓰므로 B단계 정합 테스트 대상에 넉백 시나리오 1개를 추가한다.

### 5-5. 무리 전술(공격 토큰·포위 슬롯) — 시나리오 그룹 + 정의 역할

```json
"groups": [ { "id": "pack1", "members": "wave:w1", "coordinator_hz": 2,
              "attack_tokens": 3, "ring": { "radius": 160, "slots": 8 } } ]
```

```json
"role": { "default": "melee", "when_token_denied": "hold_ring" },
"actions": [ { "id": "Slash", "considerations": [ { "input": "HasAttackToken", "curve": "Binary" } ] } ]
```

조정자는 32스텝마다 SimulationId 순으로 토큰을 배정한다(거리 오름차순, 동률 SimulationId). `HasAttackToken`·`RingSlotFree` 는 등록표 입력(D7)이며 스냅샷 값이다. 이 층은 D3 HTN 없이 성립하고, HTN 이 들어오면 조정자의 배정 규칙만 HTN 도메인으로 대체된다.

## 6. 미결 사항(사용자 결정 필요)

1. **B1 순수 커널 vs 커널 계층 규율.** 결정 기록(D13~D18)대로 월드 틱 기반을 유지하고 §1-1 의 규율만 둘지, Phase 4 에서 UObject 비의존 커널 추출을 정식 항목으로 열지.
2. **KPI 문서 소유자.** §1-4 `kpi.md` 를 기획이 소유할지, 초안을 에이전트가 쓰고 기획이 승인할지. 초기 밴드 값(예: 잡몹 1:10 승률 60~75%, 보스 45~55%)은 누가 정하는지.
3. **텔레메트리 수집 범위.** §4-4 의 플레이어 입력 다운샘플(8스텝)까지 기록할지, 이벤트만 기록할지. 저장 위치와 보존 기간.
4. **C2 반영 방식.** 04 §2.2 에 §3 C2 의 기준(적용 스텝 k, 두뇌 관측 k+N·64+1)을 병기만 할지, `cooldown`·`duration` 을 JSON 에서 "스텝 정수" 로 받아 로더가 +1 을 보정할지. 로더 보정은 만료 스텝이 적용 시점(틱 안/밖)에 의존하므로 권장하지 않는다.
5. **난이도 축 도입 시점.** Phase 2(M2-15 제안)에 넣을지, 첫 밸런스 리포트(M2-02) 이후로 미룰지.
6. **무리 전술 층의 위치.** §5-5 조정자를 Phase 3(M3-14 제안)에 넣을지, HTN(M4-01)과 함께 Phase 4 로 미룰지. 미루면 잡몹 대량 시나리오의 승률이 "동시 공격" 기준으로 산출된다.
7. **벤치 CI 임계.** §4-6 의 +20%/+50% 는 제안값이다. Phase 1 실측 후 확정할지, 처음부터 경고 전용으로 둘지.
8. **결과 보존 정책.** §4-3 의 30일·`keep` 표식·run 이름 규약을 MD-05 와 함께 확정할지. run 폴더 이름 규칙은 04 §10.4·07 M2-02·§4-3 셋이 다르므로 MD-05 결정 시 하나로 정한다.

각 구성은 같은 입력으로 프로세스 안에서 2회(rep0·rep1), 프로세스를 3회(run1·run2·run3) 실행했다. 각 회의 값 = 1024 측정 스텝의 스텝별 ns/에이전트 중앙값.

이웃 수 확인(표 3): (a)는 몸 외접원 간격 200cm 안 평균 이웃 3.6~7.4(목표 "평균 2"보다 촘촘), 실제로 고려되는 장애물(선택 수)은 M1 1.4~1.5, M2 4.2~4.9, M3·M4 6~7.4. (b)는 외접원 간격 200cm 안 이웃이 12~96으로 극단적으로 몰렸고 선택 수는 상한(5 또는 8)에 붙는다 → 과제의 "대형 이웃 6~8"은 선택 수 기준으로 충족, 원시 밀도는 그보다 훨씬 높은 최악 조건이다.

## 4. 이식 검증과 결정론

- 파이썬 원본 대조: (b) 상태 4개 × 표본 14마리 = 56결정에서 C++ M0·M2·M3p 명령이 파이썬 A(반경을 같은 값으로)·C_hzd·D_rotOBB_esc와 56/56 일치(차이 최대 0.000cm/s) — `validation_summary.txt`. 검사는 전체 순회 모드(격자 반경 제한 없음)로 했다.
- float 함정: 프로토의 원뿔 포함 검사 여유값 1e-6(double)을 float에 그대로 쓰면 경계 후보가 반올림 오차(속도 500cm/s × 6e-8 ≈ 3e-5 > 1e-6)로 "안쪽" 판정되어 M2가 파이썬과 41/56(73%)만 일치했다. 1e-3cm/s로 키우자 56/56 일치.
- 변형 대조(`variant_agreement.txt`, 같은 56상태): M3o는 M3과 56/56 같은 명령. M4는 M3과 47/56(84%) 같은 명령. M3이 희망 속도에서 벗어난 비율 12.5%, M4는 5.4%(M4는 가속 지연을 무시해 덜 보수적일 가능성 [추론]). M4의 실제 회피 품질(겹침·끼임)은 측정하지 않았다.
- 결정론: 40개 구성 모두 rep0 = rep1 해시 일치, run1·run2·run3 프로세스 간에도 해시 일치(같은 실행 파일·같은 PC). v1↔v2 해시 일치. 다른 컴파일러·CPU 간 일치(atan2f·sinf CRT 구현 차이)는 검사하지 않았다.

## 6. 판정: 300마리 4.0ms 예산 안에 들어가는가

수치는 프로세스 실행 3회 중앙값, 프레임당 = 스텝당 × 64/60(60fps, 64Hz 고정 스텝 기준 프레임당 약 1.07스텝). 괄호는 실행 3회 중 최악값.

1. **현재 코드(M0g, O(N²) 이중 순회) 자체가 예산 문서 가정보다 약 3배 비싸다.** 300마리 0.79ms(a)·0.82ms(b)/프레임(최악 0.96·1.00). 03 문서의 "분리 조향 0.26ms"(이웃당 0.1µs×8, `03-tick-and-scale.md:299,313`)는 격자 이웃 8마리 방식(M1)의 단가이고, M1 실측은 (b) 0.27ms·(a) 0.06ms/프레임으로 그 가정과 맞는다. 즉 현행 코드 기준으로는 4.0~4.7ms 추정에 약 +0.55ms가 빠져 있다 [추론: 나머지 항목은 미측정].
2. **전원(300마리) 형상 회피는 불가.** 전원 M2 1.84ms, 전원 M4 3.33ms, 전원 M3 4.13ms/프레임((b) 기준).
3. **계층안(잡몹 M1 + 길쭉·대형만 형상 회피)** 프레임당 ms:

   - "문서 추정(4.0~4.7ms, 분리 0.26ms 포함) 대비"로 보면 H4 +0.3ms, H1 +0.55~0.73ms가 늘어 4.0ms를 넘는다. 들어가려면 (i) 대형도 M2(H4)로 두거나, (ii) 형상 회피 결정을 P스텝마다 위상(Slot % P, D22)으로 나눠 계산하고 사이에는 명령을 유지(P=4면 H1이 문서 가정 대비 +0.11~0.19ms로 투영)하거나, (iii) 교전 중·이웃 존재 시에만 형상 회피를 켜는 게이트가 필요하다. M4(슬랩)는 조기 종료가 없어 7.4~11.3µs로 밀집도에 덜 민감 → 성긴 곳에서는 M3의 약 절반이지만 밀집에서는 M3과 비슷하고, 어디서나 M2의 약 2배라 "하이에나 M4"는 "하이에나 M2"보다 비싸다. M3o(삼각함수 제거)는 M3 대비 22~32% 절감. 참고로 HZD 논문의 PS4 밀집 단가 60µs/개체(`hzd_ch09.txt:352`)에 비해 같은 계열 M2가 이 PC에서 약 1/10~1/13 [추론: 기능 범위·하드웨어 차이 미보정].

## 7. 주의사항 (꾸미지 않은 한계)

1. 배경 부하 39~52% 상태에서 측정했다. 같은 프로세스 안 반복 2회는 ±1~3% 이내지만 프로세스 실행 간에는 첫 실행이 최대 약 30% 느렸다(run1 > run2 ≈ run3). 표는 3회 중앙값과 범위를 같이 적었다. 논리 CPU 2번 고정이라 같은 물리 코어의 SMT(동시 멀티스레딩) 짝 CPU 3번 부하에 영향받았을 가능성 [추론].
2. 언리얼 밖 독립 벤치다. TArray·액터·Mover·캡슐 스윕·다른 시스템의 캐시 오염이 없어 게임 안 단가는 이보다 높을 수 있다 [미검증]. 게임 자료 구조 효과는 M0g(AoS 80B·double)로만 근사했고 M0 대비 1.4~1.6배였다.
3. 운동 모델은 프로토의 비홀로노믹 적분이다. 실제 Mover(속도 즉시 꺾임 + 몸 540°/s 추종, 옆걸음)와 캡슐 물리(하이에나 중심 간격 ≥ 90cm)는 없다 → 상태 분포·조기 종료 비율이 게임과 다를 수 있다.
4. 대형 종(300×120, 180°/s)은 게임에 없는 가상 몸이다. 고블린 반경은 40(실제 고블린 캡슐 r28). 600×220 대형은 측정하지 않았다.
5. (a)의 원시 이웃 밀도(외접원 간격 200cm 안 3.6~7.4)는 목표 "평균 2"보다 촘촘하다(선택된 장애물 수는 M1 1.4~1.5). (b)는 원시 이웃 12~96으로 극단적 최악 조건이고 선택 수는 상한(5·8)에 붙는다.
6. 장애물 질의 반경 = 외접원 합 + 최대 속력×1.0초(프로토는 전체 N 순회 + 보수 시간 ≤ 3초). 반경 밖에 상위 K로 뽑힐 장애물이 있으면 프로토와 선택이 달라질 수 있다(성긴 곳 한정, 검증은 전체 순회 모드로 함).
7. Qsep·Qvo(질의만) 실행은 회피를 하지 않아 무리가 더 뭉치므로 질의 비용의 상한에 가깝다(M1 전체보다 Qsep가 비싸게 나온 이유). 질의 몫 분해는 근사로만 쓴다.
8. 과제 명세(M3 = 24방향, 장애물 ≤8)와 프로토 기본값(20방향, ≤5)이 달라 둘 다 쟀다(M3·M3p). 하이에나 M2는 장애물 ≤5.
9. M4는 이번에 새로 설계한 변형이다. 회전 껍질은 보수적이지만 가속 지연·옆걸음 감속을 무시하므로 경로 면에서는 보수적이지 않다. 품질(겹침·끼임·도달 시간)은 측정하지 않았고, M3과 같은 명령을 고른 비율 84%(56표본)만 확인했다.
10. float 이식에는 원뿔 포함 검사 여유값을 1e-6 → 1e-3cm/s로 키워야 했다(4절). 게임 이식 시 같은 함정.
11. 결정론은 같은 실행 파일·같은 PC에서만 확인했다(40구성 × 2반복 × 3프로세스 해시 일치). 다른 컴파일러·CPU·최적화 플래그 간 일치는 미검증.
12. 프레임당 값은 60fps 가정. 30fps면 프레임당 약 2.13스텝(최대 4스텝)이라 2배가 된다.
13. 벽 선분 VO(C_hzd_walls), 플레이어 비상호성, 정지·시전 몹 양보, 시전 즉시 회전, 넉백, 스폰 겹침(c에서만 일부), 경로 계층은 비용에 포함하지 않았다.
14. Git Bash에서 `cmd //c build.cmd`는 오류 없이 재빌드를 건너뛰었다(실행 파일 시각 불변). 빌드는 PowerShell `cmd /c build.cmd`로 했다.

## 1. 개념 설명 (한 문단 + 그림)

세상에 고정된 3D 격자를 플레이어 둘레에만 2~4겹 둔다. 겹마다 128×128×32칸이고 칸 크기만 두 배씩 커진다(12.5cm → 25cm → 50cm). 칸에는 '안개 그 자체'가 아니라 **잔잔한 안개와의 차이(교란) 1개 + 바람 속도 3개(x,y,z)** 만 저장한다. 잔잔한 안개는 지형 높이에서 바로 나오는 식(땅 위 높이에 따른 농도 + 움푹한 곳 가중)이라 저장도 계산도 필요 없다. 풀이는 게임에서 가장 흔하고 튼튼한 방식(Stable Fluids: 한 프레임 전 위치를 거슬러 가서 값을 가져오기 + 횟수를 고정한 압력 풀이)을 3D로 쓰되, **흔들림이 남아 있는 덩어리만** 목록으로 뽑아 그 개수만큼만 GPU에 일을 시킨다. 잠든 덩어리는 값이 0이고 아무도 손대지 않는다. 그리기는 가까운 곳(약 24m 안)을 우리 화면 칸으로 한 번 적분해 화면에 얹고, 먼 곳과 창 밖은 지금처럼 엔진 볼륨 안개가 같은 평형 식으로 그린다.


'전체를 훑지 않고 주변만 본다'가 세 군데에서 일어난다.

|---|---|---|

빌려 온 것과 이 게임에 맞게 바꾼 점(사용자 요구 '남의 알고리즘도 최적화해서 쓴다')

| 빌려 온 것 | 원래 모습 | 여기서 바꾼 점 |
|---|---|---|
| Stable Fluids (Stam 1999) | 안개 농도 전체를 풂 | 교란만 풂. 압력 반복 8~12회 고정 + 지난 프레임 압력에서 시작. 프로젝트 2D의 '타일 + 가장자리를 공유 메모리에 올려 묶어 반복' 방식을 3D로 옮기되 크기를 바꾼다: 2D는 가장자리 4칸·4회(24² = 576칸), 3D는 그대로면 16³ = 4,096칸이라 공유 메모리에 안 들어가므로 **덩어리 8³ + 가장자리 2칸(12³ = 1,728칸)·디스패치당 2회**. 칸·회당 읽기는 2D 0.56 → 3D 1.69, 묶지 않으면 7 [계산] |
| NVIDIA Flow식 희소 블록 | 블록 표 + 3D 아틀라스(주소 변환 필요) [조사04] | 메모리는 빽빽하게 두고 '깨어 있음 깃발'만 희소. 이웃 주소가 번호 ±1 그대로라 주소 변환 손실(처리량 5~50%로 하락 [조사05])이 없음 |
| 클립맵 + 환형 주소 | 지형·전역 조명용 | 창이 움직여도 복사 0. 새로 들어온 1덩어리 두께 판만 초기화 |
| 대기 모델의 '기준 상태 + 변화량' | 날씨 계산 | 기준 상태 = 지형에서 바로 나오는 안개 식. 그래픽스 쪽 직접 선례는 못 찾음 [조사06 추정] |
| 화면 칸 안개 (Wronski 2014, Hillaire 2015) [조사07] | 지난 프레임을 90~95% 섞어 반응이 느림 | 섞는 비율을 50% 이하로, 깊이 간격을 시점별로 직접 지정 → 칼 반응 지연 제거 [추정] |

기술적으로 되는지 직접 확인한 것
- RDG 컴퓨트 패스는 간접 디스패치를 지원한다 [확인: Engine/Source/Runtime/RenderCore/Public/RenderGraphUtils.h:647-685]. 다만 프로젝트 GPU 코드에는 선례가 없다 [확인: Source/TDFluidGpu/Private에서 IndirectArgs·DispatchIndirect 검색 0건]. 프로젝트가 쓰는 것은 'CPU가 만든 목록 길이만큼 디스패치'다 [확인: Source/TDFluidGpu/Private/TDFluidGpuStepPasses.cpp:2613].
- 엔진 볼륨 안개 자신이 3D 텍스처를 RGBA 16비트 실수 + 쓰기 가능으로 만든다 [확인: Engine/Source/Runtime/Renderer/Private/VolumetricFog.cpp:1403-1407]. 같은 포맷의 3D 쓰기 텍스처가 이 엔진에서 돈다는 간접 증거다(우리 패스·이 카드에서의 동작은 단계 0에서 확인).
- 볼륨 렌더 타깃 에셋에 '쓰기 가능' 스위치가 있다 [확인: Engine/Source/Runtime/Engine/Classes/Engine/TextureRenderTargetVolume.h:54 `bSupportsUAV`]. 우리 3D 결과를 재질이 읽는 텍스처로 내보낼 길이 있다는 뜻이다. 볼륨 재질의 복셀화 패스에서 실제로 읽히는지는 미검증 [조사02].
- 엔진이 화면 칸 적분 결과를 뷰 자원으로 들고 있고 [확인: Engine/Source/Runtime/Renderer/Private/SceneRendering.h:858], 적분 전의 칸별 산란 값도 다음 프레임용 이력으로 뷰 상태에 남긴다 [확인: VolumetricFog.cpp:2038]. 앞의 것은 프로젝트의 TDFogScattering이 이미 읽는다 [조사02]. 뒤의 것이 8절 위험 3의 '엔진 조명 빌리기' 후보다.

## 2. '평형'과 '교란'을 나눠 다루는 법

```
 화면에 그리는 농도 = max(0, 평형(x) + 교란(x)) × 흐름에 끌려가는 무늬(3D 노이즈)

 평형(x) = 기준 농도 × 높이 곡선(땅 위 높이) × 고임 가중(움푹한 정도)   ← 식. 저장·계산 0
 교란(x) = 칸에 저장하는 16비트 실수 1개. 건드린 곳만 0이 아님          ← 이것만 계산
```

```
 옆에서 본 단면

 높이
 3m │                   ▲ 솟은 덩이(+)
 2m │ ─ ─ ─ ─ ─ ─ 평형 안개 윗면(식) ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
 1m │ ░░░░░░░░░░   (−)   ░░░░░░░░░░ ┌─── 상판 ───┐ ░░░░░░░
 0m │ ░░░░░░░░ 칼이 판 골 ░░░░░░░░░ │ ░ 밑 공간 ░ │ ░░░░░░░
    └──────────────────────────────┴────────────┴────────→
     저장하는 값 = 실제 − 평형. 안 건드린 곳은 0 → 잠든 덩어리
```

교란이 생기는 길 3가지(눈에 보이는 변화의 원천)
1. **지우기·밀어내기**: 몸·칼·파편이 지나간 부피에서 농도를 덜고(−) 속도를 준다.
2. **위아래 섞임**: 평형은 아래가 진하고 위가 옅다. 3D 바람이 아래 안개를 위로 올리면 위에는 +(솟은 덩이), 아래에는 −(구멍)가 저절로 생긴다. 지금 2D로는 원리상 못 내는 장면이다. 계산은 '실제 안개'를 옮기고 차이만 저장한다: `새 교란(x) = 교란(출발점) + 평형(출발점) − 평형(x)`. 평형은 높이 지도 한 번 읽기로 끝나므로 싸다 [추정].
3. **무늬 끌림**: 그릴 때 노이즈 좌표를 바람 방향으로 살짝 당겨 실오라기가 흐름을 따라가게 한다. 저장 채널 추가 없음. 지금 HVOL(엔진 이질 볼륨) 경로가 2D 속도로 하던 것의 3D판이다 [조사01].

다시 차오르는 길 3가지

| 길 | 쉬운 설명 | 역할 |
|---|---|---|
| a. 흘러듦(무게) | 교란이 +면 아래로, −면 위로 미는 힘 한 줄. 솟은 덩이는 가라앉아 낮은 곳으로 퍼지고, 구멍은 옆·위 안개가 밀려와 메움 | 자연스러움 |
| b. 가장자리 번짐 | 약한 확산. 구멍이 가장자리부터 닫힘 | 자연스러움 |
| c. 서서히 복원 | 교란 × e^(−dt/τ), τ 3~6초, 위치마다 조금 다르게(얼룩지며 차오름) | '언제나 끝난다'는 보증 → 덩어리가 반드시 다시 잠듦 |

세 값(힘·확산·τ)은 모두 JSON 데이터로 둔다(프로젝트 규칙 '값은 데이터' [조사01]).

잠들기와 깨우기(누가 정하나)
- 1차안은 **CPU 타이머**다. CPU는 입력(몸·칼·파편)이 어느 덩어리에 닿았는지 이미 안다. 닿은 덩어리와 닿을 범위의 이웃을 '복원 시간 τ + 여유' 동안 깨워 두고, 끝나기 1초 전부터 감쇠를 세게 걸어 값이 0(화면 밝기 1/255 미만)에 닿은 뒤 재운다. 프로젝트 GPU 코드의 '목록 길이만큼 디스패치' 방식 그대로라 새 기술이 없다 [추정].
- GPU가 실제 흔들림을 재서 스스로 목록을 만드는 방식(간접 디스패치)은 더 정확하지만 프로젝트에 선례가 없다. 타이머 방식의 낭비(이미 잔잔한데 깨어 있는 덩어리)가 측정으로 크다고 나온 뒤에만 올린다.
- 이웃은 무조건 한 덩어리씩 넓히지 않는다. 작은 사건 하나가 27덩어리가 되기 때문이다 [계산: 3×3×3]. 입력의 반경과 속도로 닿을 범위만 깨운다.

정직한 주의 2개
- 균일한 안개는 휘저어도 안 보인다 [조사06 추정]. 수평으로 휘젓는 장면은 1번(지우기)과 3번(무늬)에 기대야 한다.
- 진짜 3D가 되면 **허리 높이 수평 베기는 무릎 높이 안개를 거의 안 건드린다**(물리적으로는 맞음). 지금 2D의 '높이 페이드' [조사01]보다 엄격해진다. 안개 두께(예 1.2~1.5m)와 '칼바람 반경' 값을 연출로 정해야 한다 [추정].

낮은 곳 고임: 평형 식의 고임 가중 = (주변 평균 높이 − 내 높이)를 0~1로 자른 값. 높이 캡처 텍스처를 흐리게 한 것과의 차이로 GPU에서 즉석 계산하므로 오프라인 굽기가 없다 [추정]. 흐트러진 안개가 비탈을 타고 '흘러가는' 움직임은 a(무게)와 지형 경계가 만든다. 압력 풀이가 덜 수렴하면 이 흐름이 약해진다는 경고가 있어 [조사06 추정] 반복 횟수는 단계 0의 단면 시제품에서 정한다.

### 5.1 환산 식 (조사 01의 실측에서 출발)

```
 실측(RTX 2060, 물 GPU 2D 한 스텝, 오프스크린)        192² 0.135 / 512² 0.318 / 1024² 0.982 ms   [조사01]
 두 점 직선                                            기울기 0.84 ms/Mcell, 고정 0.10 ms          [조사01 추정]
   (검산: 192² 예측 0.10 + 0.84×0.0369 = 0.13, 실측 0.135)                                         [계산]
 2D → 3D 배수 k = 2~3 (이웃 4→6, 속도 성분 2→3)                                                    [조사01 추정]
 3D 한 스텝 계수 c = 0.84 × k = 1.7 ~ 2.5, 중심 2.1 ms/Mcell.  비관 4.0(3D 텍스처 접근이 흩어질 때) [추정]

 계산 시간 = 고정 + c × 프레임당 계산 칸(백만)
 프레임당 계산 칸 = Σ겹 ( 깨어 있는 덩어리 수 × 512 × 갱신 주기 비율 )
 고정 = 0.10 ms × 프레임당 평균 갱신 겹 수  → 2겹 0.15 / 3겹 0.18 / 4겹 0.28 ms                    [추정]
```

교차 점검 [추정]
- 출발점의 무게: 0.84 ms/Mcell을 낸 물 스텝은 가벼운 스텝이 아니다. 이름이 다른 패스가 23종 보이고(조건부 포함) 반해상도 압력 준비·적용, 평균 제거, 이류, 잔물결 부분 걸음까지 들어 있다 [확인: Source/TDFluidGpu/Private/TDFluidGpuStepPasses.cpp:2613-3509]. 우리 3D 스텝(옮기기 1~2 + 힘·발산 1 + 압력 4~6 + 기울기 빼기 1 = 디스패치 7~10개)에 배수 2~3을 곱하는 것은 넉넉한 쪽이다.
- 싼 쪽: 엔진 볼륨 안개가 415만 칸을 1.08~1.52ms에 돈다 = 0.26~0.37 ms/Mcell(조명 포함) [조사01]. 3D 패스 3~4개 분량으로 보면 패스 1개 ≈ 0.07~0.12 ms/Mcell이고, 우리 스텝을 패스 8~10개 분량으로 보면 0.6~1.2 ms/Mcell.
- 비싼 쪽: 나이아가라 3D 기체 64³이 약 1.8ms(카드 미상) [조사06 요약만] = 6.9 ms/Mcell [계산]. 범용 구현처럼 패스가 많으면 비관값 4.0도 넘는다.
- 최신 논문과의 거리: Leapfrog Flow Maps는 RTX 4090에서 419만 칸 11.7~14.1 ms/스텝 [조사05]. 우리는 프레임당 18만~40만 칸만 계산하므로 칸 수가 10~20분의 1이다.

먼 곳용 엔진 볼륨 안개를 '높음' 등급(16픽셀·64층, 522,240칸 [조사02])으로 낮추면 1.52 × (0.522 ÷ 4.147) = 0.19ms [계산: 칸 수 비례 가정] + 고정비 미상 → 0.2~0.5ms로 본다. 격자별 비용 곡선은 프로젝트에서 아직 안 쟀다 [조사01]. 엔진 안개 전역값은 사용자 결정 대기 항목이라 [조사01] 이 낮춤은 제안일 뿐이다.

자릿수 점검: Hillaire 2015는 PS4 900p에서 화면 칸 안개 합계가 16×16 타일 0.83ms, 8×8 타일 2.95ms [조사07]. 조명 포함·다른 기기라 직접 비교는 못 하고 자릿수만 맞는다.

### 5.5 합계와 지금 대비 (전투 중)

| | 계산 | 자체 그리기 | 엔진 안개(높음) | 합계 | 지금(약 1.68ms) 대비 |
|---|---|---|---|---|---|
| 탑다운 | 0.54 (0.46~0.89) | 0.35~0.6 | 0.2~0.5 | 1.0~2.0 (중심 1.4) | −0.7 ~ +0.3 |
| 3인칭 | 0.59 (0.52~0.97) | 0.5~0.8 | 0.2~0.5 | 1.2~2.3 (중심 1.6) | −0.5 ~ +0.6 |
| 1인칭 | 1.12 (0.96~1.89) | 0.6~1.0 | 0.2~0.5 | 1.8~3.4 (중심 2.3) | +0.1 ~ +1.7 |

- 지금 = 엔진 볼륨 안개(에픽 등급) p50 1.52ms [조사01] + 2D 안개 계산 약 0.16ms [계산].
- 여유 = 60프레임 16.67ms − 안개 무대 총 GPU 14.7~15.0ms [조사01] = **1.7~2.0ms** [계산]. 에디터 안 실행 수치라 보수적일 수 있다 [조사01].
- 읽는 법: 새 돈을 쓰는 게 아니라 **지금 엔진 안개에 쓰는 1.5ms를 갈아 끼우는** 구조다. 탑다운·3인칭은 비관값에서도 여유 안, 1인칭은 비관값(+1.7)이면 여유를 거의 다 쓴다.
- 창 이동: 겹0이 1m 움직일 때 새로 들어오는 판은 16×4 = 64덩어리 = 32,768칸 [계산]. 지우기 + 막힘 굽기 두 패스라 0.01ms대 [추정]. 지금 2D처럼 격자를 통째로 옮기는 패스(모으기·뿌리기 두 번 [조사01])가 아예 없다. 2D 안개 쪽 이동 비용은 미측정이라 [조사01] 얼마나 이득인지는 숫자로 말할 수 없다.

| 탑다운 | **85%** | 보이는 바닥 약 210㎡가 16~32m 창 안에 다 들어오고, 환산 합계 1.0~2.0ms가 지금 안개 비용(약 1.7ms)과 비슷하다. 남은 15%는 '3D 한 스텝 실측'과 '위에서 보면 3D 이득이 작게 보일 수 있음' |
| 3인칭 | **65%** | 계산은 탑다운과 거의 같다(+0.05ms). 걸림돌은 그리기: 조명 일치, 겹 3개의 이음매, 먼 곳 넘겨주기. 조명이 안 맞으면 엔진 주입 경로(지연 0.11~0.36초 [조사02 계산])로 물러나는 길이 있다 |
| 1인칭 | **40%** | 근접 겹 때문에 계산이 약 2배(1.1ms), 합계 비관값 3.4ms가 여유를 다 쓴다. 눈앞 칸 크기와 회전 흔들림은 비용이 아니라 원리의 문제라 돈으로 못 푼다 |

권고: 구조는 세 시점 공통으로 잡되, **탑다운을 먼저 완성하고 3인칭은 단계 3~4의 숫자를 본 뒤, 1인칭은 단계 5에서 따로 판정**한다. 세 시점을 한꺼번에 약속하지 않는다.

## 10. 이 문서의 한계

- 실행·측정을 하지 않았다. 5절의 모든 ms는 2D 물 실측과 엔진 안개 실측에서 환산한 값이고, 2D → 3D 배수(2~3)와 깨어 있는 덩어리 비율(8~29%)이 가장 약한 고리다.
- 원문을 직접 연 것은 [확인] 표시가 붙은 엔진 파일 4개와 프로젝트 파일 3개뿐이다. 나머지 사실은 조사 보고서 01~07의 표기를 그대로 믿고 인용했다.
- 공유 메모리 반복이 3D에서 한도 안에 드는지는 계산만 했다. 덩어리 + 가장자리 2칸 = 12³ = 1,728칸 × (압력 2벌 + 발산) × 4바이트 = 약 21KB, 프로젝트 2D처럼 가장자리 4칸이면 16³ = 4,096칸 × 12바이트 = 약 49KB [계산]. 그룹 공유 메모리 한도 32KB는 기억에 의존한다 [추정, 미확인]. 가장자리 1칸에 낡은 값으로 4회 도는 근사안과 어느 쪽이 나은지는 단계 0에서 잰다.
- '엔진 조명 빌리기'(엔진 화면 칸을 빛 탐침처럼 쓰기)는 착상 단계다. 적분 전 칸별 산란 값이 뷰 상태 이력으로 남는 것까지만 확인했다 [확인: VolumetricFog.cpp:2038]. 그것을 우리 패스에서 읽으려면 비공개 뷰 상태 접근이 하나 더 필요하고, 한 프레임 늦은 값이며, 거기서 '빛만' 되찾는 계산이 맞는지는 해 보지 않았다 [추정].
- 자체 화면 칸(단계 3)에서 엔진 안개 결과나 조명을 읽는 부분은 엔진 비공개 헤더에 기댄다(TDFogScattering과 같은 방식 [조사02]). 엔진 버전을 올리면 깨질 수 있다 [조사02 추정]. 엔진 안개에 주입하는 길(단계 1)은 재질과 메시만 쓰므로 이 위험이 없다 [추정].
- 다른 설계자의 문서는 보지 않았다.

# 09. 완결성 비평 — 진짜 3D 볼륨 안개 가능성 검토 (조사 01~07 대상)

- 작성: 2026-11-12 claude(하위 에이전트, 읽기 전용). 도구 호출 약 25회. 코드·에셋·장부는 건드리지 않았다.
- 표기: [확인: …] = 이 세션에서 원문을 직접 열어 대조함. [보고서 NN] = 그 조사 보고서의 주장을 옮김(확실성은 그 보고서 표기를 따름). [추정]·[내 계산] = 내 추론·산수. 미확인 = 근거 못 찾음.
- 약어: GPU = 그래픽 처리 장치. Mcell = 칸 100만 개. LBM = 격자 볼츠만 방법(Lattice Boltzmann Method, 압력 풀이가 없는 유체 계산법). LFM = Leapfrog Flow Maps(2025년 논문의 풀이). GDF = 전역 거리장(Global Distance Field). HV/HVOL = 이질 볼륨(Heterogeneous Volumes). froxel = 카메라 시야 모양 칸. PIE = 에디터 안 플레이. VRAM = 그래픽 카드 메모리. UAV = 컴퓨트 셰이더가 쓸 수 있는 텍스처.

## 0. 한눈에 보기

```
가능성 판정 = [1] 계산 비용   x  [2] 그리기 비용  x  [3] 화질(조명·합성)  x  [4] 눈에 보이는 이득
              근거 충분          숫자 0개           추정뿐                 시점마다 다름
              (4갈래가 일치)     (가장 큰 구멍)     (엔진 빛을 못 받음)     (탑다운 작음 / 3·1인칭 큼)
```

1. 조사 7건은 [1] 계산 비용은 잘 세웠다. 서로 다른 근거 4갈래가 RTX 2060에서 "칸 100만 개 한 걸음 약 1~2.5ms(게임용 단순 풀이)"라는 같은 자릿수를 가리킨다 [추정: 1-2절].
2. [2] 그리기 비용은 숫자가 하나도 없고 [3] 화질은 전부 추정이다. 이 둘이 비어 있으면 "가능성 몇 %"를 말할 수 없다.
3. 프레임 여유가 이미 좁다. 안개 무대 전체 GPU 시간 중앙값 14.63~15.05ms [확인: Saved/AgentOps/20261110/fog-terrain/cost/c1_summary.json:17,94,171,248,325,402,479,556] → 초당 60장(16.67ms) 기준 남는 시간 1.6~2.0ms [내 계산]. 새 안개가 "추가"인지 "교체"인지가 판정의 절반이다. 어느 보고서도 예산 목표를 정하지 않았다.
4. 보고서마다 격자 전제가 달라(12.8만~419만 칸, 33배 차이) 같은 물건을 두고 "가능"이라 말하고 있지 않다. 지금 2D 안개의 가로 칸은 15.6cm인데 [보고서 01], 3D 제안의 25~50cm 칸은 지금보다 가로로 흐리다. 이 기준선을 말한 보고서가 없다.
5. "탑다운에서는 진짜 3D 이득이 안 보인다"는 반론은 탑다운만 놓고 보면 대체로 맞다. 진짜 3D의 값어치는 (가) 3인칭·1인칭이 실제 일정인지 (나) 실내·다리·동굴처럼 위아래로 겹친 공간이 있는지에 달려 있다(5절).
6. 직접 대조로 바뀐 것 네 가지: 엔진 안개의 지연은 밀도에도 걸린다(추정→확인). "2060은 4090의 3분의 1"은 실측표로 3.1~3.35배 확인, 단 최악은 12배. LFM의 "압력 7.9ms"는 원문 확인, 그러나 "그리기 포함"과 "trimming 2배 = 건너뛰기 근거"는 잘못 읽은 것으로 보인다. 조사 06의 "칸 수 10분의 1이면 1~2ms"는 자기 숫자와 안 맞는다(실제로는 21~42분의 1).

### 1-2. 계산 비용: 서로 다른 근거 4갈래를 같은 단위로 놓기

| 근거 | 원래 값 | RTX 2060에서 Mcell당 |
|---|---|---|
| 자체 측정, 물 2D 한 스텝 전체 | 0.84ms/Mcell + 고정 0.10ms [보고서 01: 직선 맞춤 추정] | 3D는 칸당 2~3배 가정 → 1.7~2.5ms [보고서 01: 추정] |
| 이 PC의 엔진 볼륨 안개(415만 칸, 조명 포함) | 1.08~1.52ms [확인] | 0.26~0.37ms (무거운 패스 묶음 1회) |
| FluidX3D LBM, RTX 2060 실측표 | 3,571~3,604 MLUPs/s [확인] | 0.28ms (한 걸음, 최적화된 OpenCL·빈 상자) |
| LFM 다중격자 V-cycle 1회(4090, 256³에서 0.81ms [확인]) | 0.048ms/Mcell | x3.2 → 0.155ms [내 계산] |
| LFM 한 걸음 전체(4090) | 2.4~3.4ms/Mcell [확인] | x3.1~3.35 → 7.5~11.3ms [내 계산] |

읽는 법 [추정]: 무거운 패스 1회가 약 0.15~0.4ms/Mcell. 게임용 단순 풀이(이류 2 + 힘 + 발산 + Jacobi 8~20회 + 기울기 = 패스 7~10회 상당)는 약 1~2.5ms/Mcell, LFM급 정밀 풀이는 8~11ms/Mcell.

예산 1.5ms에 들어가는 칸 수 [내 계산]: 단순 풀이 60만~150만 칸, LFM급 13만~20만 칸. 조사 06의 "14.1ms x 3배 → 칸 수를 10분의 1(20만~60만 칸)로 줄이면 1~2ms"는 산수가 안 맞는다. 42ms를 1~2ms로 만들려면 21~42분의 1(10만~20만 칸)이다.

## 3. 서로 어긋나거나, 근거가 약한데 결론을 좌우하는 주장 8개

**C1. 격자 크기 전제가 보고서마다 다르다 (모순)**
- 주장: 01은 40m x 3m·25cm = 30.7만 칸 [확인: 01-project-current.md:109], 05는 32m x 8m·12.5cm = 419만 칸(25cm면 52만), 06은 40m x 10m·50cm = 12.8만 칸(25cm면 약 100만).
- 왜 중요한가: "가능"의 대상이 33배 다르다. 지금 2D 안개는 256²·창 40m·칸 15.6cm다 [보고서 01]. 같은 가로 선명도를 3D로 유지하면 256x256x8층 = 52만, 16층 = 105만, 32층 = 210만, 64층 = 419만 칸이다 [내 계산]. 50cm 칸은 지금보다 3.2배 거칠다.
- 어디서 확인하나: 부모가 설계 기준점 하나(가로 범위·세로 범위·칸 크기·층 수)를 정해 모든 숫자를 다시 환산. 세로 범위는 G3의 고저차 자료로.

**C2. "RTX 2060은 RTX 4090의 3분의 1" (추정 → 부분 확인)**
- 왜 중요한가: 남의 논문 숫자를 이 PC로 옮기는 유일한 환산 계수다.
- 결과: LBM 실측표로 3.08~3.35배 확인(1-1절 2번). 계산이 병목이면 최대 12.3배.
- 어디서 확인하나: 환산을 그만두고 이 PC에서 3D 더미 패스를 직접 잰다.

**C3. LFM 숫자의 해석 (요약·역산 → 원문 확인, 두 군데 정정)**
- 왜 중요한가: "압력이 절반 이상이니 압력을 줄이는 것이 핵심"과 "타일 건너뛰기 2배"라는 두 설계 판단의 뿌리다.
- 결과: 압력 7.9/14.1ms = 56% 확인. "그리기 포함"은 의심, "trimming"은 건너뛰기가 아니라 계수 읽기 생략(1-1절 3a·3b). "10분의 1" 산수 오류(1-2절).
- 어디서 확인하나: https://wrc042.github.io/assets/sig25lfm.pdf 8~9쪽 표를 사람이 눈으로 한 번 더(추출 글자가 깨져 열 이름은 내가 확정하지 못함).

**C4. "패스 1회 0.06~0.08ms/Mcell", "3D는 칸당 2~3배" [보고서 01: 둘 다 추정, 패스 수 미확인]**
- 왜 중요한가: 이 PC에서 나온 유일한 계산 기준이고, 시범 격자 30.7만 칸 0.6~0.9ms 추정의 바탕이다.
- 어디서 확인하나: `Source/TDFluidGpu/Private/TDFluidGpuStepPasses.cpp`의 패스 목록과 `Docs/Validation/FluidFX/FX-4b-budget-2026-10-24.json`(경로는 보고서 01 기준, 나는 열지 않음). 패스별 시간표(TDFluidGpuPassTimestamps.h)가 있으면 그 값이 가장 정확하다.

**C5. "밀집 메모리 + 8x8x8 활동 덩어리만 계산하면 5~10배 절감(활동 10~20% 가정)" [보고서 05: 추정]**
- 왜 중요한가: 최적화 계획의 중심이다. 그런데 확인된 숫자는 없다. 근거로 든 LFM의 2배는 다른 기법이다(C3).
- 추가 구멍: 큰 전투(몬스터 여럿 + 파편)에서는 활동 비율이 50~100%가 될 수 있다. 평균이 아니라 최악에 맞춰 예산을 잡아야 한다 [추정]. 잠든 이웃을 0으로 두는 압력 경계의 화면 이상도 미측정 [보고서 05도 인정].
- 어디서 확인하나: 측정(활동 5/20/50/100%), 그리고 G10의 2D 선행 실험.

**C6. "엔진 볼륨 안개 재질·HV 재질이 런타임 3D 텍스처를 읽는다" [보고서 02: 미검증]**
- 왜 중요한가: 되면 엔진 조명을 공짜로 받는 길(경로 A·C)이 열리고, 안 되면 자체 레이마칭(경로 E)과 조명 직접 구현이 강제된다.
- 결과: 클래스 수준은 확인(1-1절 5번). 단 경로 A는 되더라도 지연이 확인됐다(1-1절 1번).
- 어디서 확인하나: 에디터 10분 시험(6절 F4).

**C7. GDF를 장애물 입력으로 쓰는 전제들 [보고서 03: 칸 19.8cm 추정, 캐릭터·파편 미반영 추정, 생성 여부 미확인]**
- 왜 중요한가: GDF를 보조 입력으로 쓰면 "GDF가 매 프레임 있다"는 전제가 필요한데, 조건부 생성임을 확인했다(1-1절 8번). 우리 패스가 읽으려면 "필요함" 표시를 세우는 방법이 추가로 필요하다 [추정].
- 어디서 확인하나: DistanceFieldAmbientOcclusion.cpp:783-830, GlobalDistanceField.cpp의 겹 범위 계산부. 권고안(지형 높이 지도 + 충돌 도형 굽기)은 GDF 없이도 성립하므로 우선순위는 낮다.

**C8. "LBM은 1ms에 약 380만 칸, 100만 칸 창도 가능성" [보고서 06: 추정]**
- 왜 중요한가: 압력 풀이를 없애는 유력 후보다.
- 결과: 카드 성능 숫자는 확인(3,571~3,604). 그러나 한 프레임에 필요한 걸음 수가 칸 크기에 반비례한다. 칼끝 10m/s, 15.6cm 칸이면 2.7~10.7걸음 [내 계산]. 105만 칸 x 2.7~10.7걸음 = 0.8~3.1ms(최적화 OpenCL 수준일 때), 엔진 셰이더로 그 절반 효율이면 1.6~6.2ms [추정]. LBM은 거친 칸에서만 싸다.
- 어디서 확인하나: 조사 06 본문 44~45행의 가정을 칸 15.6·25·50cm로 다시 계산해 표로.

부록(작은 불일치): 조사 04의 메모리 어림은 128³ 67MB인데 256³ 약 1GB다. 칸 수는 8배이므로 약 536MB가 맞다 [내 계산]. 결론에는 영향이 작다. "희소 격자"라는 말도 02(경로 E 이름)와 05(본격 희소는 손해)가 다르게 쓴다(7절).

## 5. "탑다운에서는 진짜 3D의 이득이 눈에 잘 안 보인다" 반론 평가

### 5-1. 먼저 숫자: 탑다운 카메라가 세로 구조를 얼마나 보는가

전제는 조사 02의 구도다(스프링 암 800cm, 60도 내려봄, 1920x1080, 가로 시야 90도 가정). 높이 h인 점이 바닥 점에서 화면상 얼마나 떨어져 보이는가 = h x cos(광선이 바닥과 이루는 각) ÷ 그 깊이의 픽셀 크기 [내 계산].

| 화면 위치 | 광선-바닥 각 | 픽셀 크기 | 30cm 안개 | 90cm 안개 |
|---|---|---|---|---|
| 아래 끝 | 89.4도 | 0.63cm | 0.5픽셀 | 1.5픽셀 |
| 가운데 | 60도 | 0.83cm | 18픽셀 | 54픽셀 |
| 위 끝 | 30.6도 | 1.23cm | 21픽셀 | 63픽셀 |

- 세로 구조는 안 보이는 것이 아니라 수십 픽셀로 보인다. 다만 지금 2D도 "밀도로 높이를 만드는 규칙 + 3D 노이즈"로 기둥을 세워 그리므로 [보고서 01] 이 시차는 이미 흉내 낸다. 진짜 3D가 더하는 것은 "높이별로 다르게 움직임"뿐이다.
- 책상 아래: 높이 75cm 책상이면 카메라 쪽 가장자리에서 43cm 안쪽까지만 바닥이 보인다 [내 계산: 75 ÷ tan60°]. 책상 아래 안개는 탑다운에서 대부분 상판에 가려진다.

### 5-3. 판정 [추정]

- 탑다운만 본다면 반론은 대체로 맞다. 눈에 띄는 이득은 "겹친 공간(실내·다리·동굴)에서의 올바름"과 "높이별 움직임" 정도이고, 나머지는 2D 보강으로 흉내 낼 수 있다.
- 반론이 결정적이지 않은 이유는 두 가지다. 사용자 목표에 3인칭·1인칭이 들어 있고, 2D 기둥 모델이 이 프로젝트에서 이미 높이 문제로 여러 번 우회책을 필요로 했다.
- 판정에 반영할 설계 함의: (가) 세로 층 수를 손잡이로 둔다(탑다운 8~16층, 다른 시점에서 늘림). (나) 구현 전에 같은 사건을 2D와 3D 참고 영상으로 탑다운 구도에서 나란히 보여 사용자가 차이를 고르게 한다. 못 고르면 3D 계산은 3인칭 일정이 잡힐 때로 미루고 지금은 2D 보강이 답이다.

## 7. 사용자에게 말하기 전에 정리할 것

### 7-1. 말 통일
- "희소 격자"가 두 뜻으로 쓰였다. 조사 02는 본선 경로 이름에 "세상 고정 희소 격자"를 쓰고, 조사 05는 "본격 희소 구조(해시·VDB)는 이 크기에서 손해, 메모리는 꽉 채우고 계산만 골라서"라고 결론 냈다. 사용자에게는 한 문장으로: "메모리는 통째로 잡아 두고, 계산은 움직임이 있는 덩어리에서만 한다. 사용자가 말한 주변 칸만 처리는 채택, 희소 자료구조 자체는 창이 1천만 칸을 넘을 때의 다음 단계" [보고서 05 근거].
- "가능"의 대상을 하나로 고정해 말한다(C1). 예: "가로 40m, 칸 15.6cm, 세로 N층".

### 7-2. 사용자만 답할 수 있는 질문 5개
1. 목표 프레임은 60인가 30인가. RTX 2060은 최소 사양인가 권장 사양인가.
2. 3인칭·1인칭은 실제 일정에 있는가, 열어 두기만 하면 되는가.
3. 안개는 순수 장식인가, 시야·은신 같은 게임 규칙에 쓰이는가.
4. 새 3D 안개를 켤 때 무엇을 끄는가(엔진 볼륨 안개, 기존 2D 안개 중).
5. 원하는 그림의 참고 장면 2~3개(수용 기준의 재료).

### 7-3. 구멍을 메우는 가장 싼 순서 [추정]
```
[0] 지금 것 재기          : 기존 안개 계산 단독 ms, 전투 장면 여유, 엔진 경로 반응 지연  (F1, F4-나)
[1] 3D 더미 계산 재기     : 256x256x8/16/32층에서 이류 2 + Jacobi 8/20 + 기울기           → 계산 ms/Mcell 확정
[2] 더미 그리기 재기      : 3D 텍스처 1장을 절반 해상도로 행진, 탑다운·3인칭·1인칭       → 그리기 ms 확정
[3] 2D에서 건너뛰기 실험  : 차이만 계산 + 잠자는 덩어리, 이음매·튐 확인                   → 절감 배수 확정

```
[0]~[2]가 끝나면 R1이 닫히고, [3]은 R5, [4]는 R3을 닫는다. 측정은 프로젝트 관례대로 사전 등록 뒤 진행한다 [보고서 01].
